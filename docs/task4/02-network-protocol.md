# Сетевой протокол

Документ фиксирует формат обмена между `matching-engine-server` и клиентом до того, как написан сетевой код: формат кадра, состав запроса и ответа, устройство `Server` и `Session`, время жизни асинхронных операций и набор тестов, которыми протокол проверяется.

Покрывает `REQ-DOC-08`. Соответствующие требования указаны у каждого раздела — это же и есть перечень того, что проверяется в реализации.

Последовательность остановки сервиса, потоки и обработка сигналов описаны отдельно, в `01-service-lifecycle.md`; здесь только то, что видно на проводе и в сессии.

---

## 1. Формат кадра

TCP не сохраняет границы сообщений: один вызов `write` на стороне клиента может прийти сервером за три чтения, а три вызова `write` — за одно. Поэтому границу сообщения задаёт не транспорт, а собственный формат кадра (`REQ-PROTO-01`).

```
 0       1       2       3       4                        4 + N
 +-------+-------+-------+-------+------------------------+
 |          размер N (uint32)    |   полезная нагрузка    |
 |        сетевой порядок        |    ровно N байт JSON   |
 +-------+-------+-------+-------+------------------------+
```

| Свойство | Значение |
|---|---|
| Заголовок | 4 байта, `uint32_t` — длина полезной нагрузки (`REQ-PROTO-02`) |
| Порядок байт | сетевой, старший байт первым (`REQ-PROTO-03`) |
| Полезная нагрузка | ровно N байт: один JSON-объект в UTF-8, без завершающего перевода строки |
| Максимальный размер | `server.max_message_size` из конфигурации, по умолчанию 1 МБ (`REQ-PROTO-08`) |

Длина в заголовке — это длина **только** полезной нагрузки; сами четыре байта заголовка в неё не входят. Кадр целиком занимает `4 + N` байт.

**Порядок байт указан явно и по делу.** На машине с прямым порядком байт (`x86-64`, где проект и собирается) реализация, забывшая преобразование, будет успешно разговаривать сама с собой: записанное без `htonl` значение прочитается без `ntohl` и совпадёт. Поэтому корректность проверяется не round-trip'ом, а побайтовым содержимым заголовка: для длины 1 первым байтом обязан идти `0x00`, четвёртым — `0x01`.

### 1.1. Максимальный размер и защита от заявленного гиганта

Размер проверяется **сразу после разбора четырёх байт заголовка и до любого выделения памяти под тело** (`REQ-PROTO-09`). Клиент, объявивший в заголовке 2 ГБ, не должен вызывать попытку выделить 2 ГБ: до аллокации дело не доходит, потому что проверка стоит раньше.

Значение берётся из конфигурации, а не зашивается константой: администратор установленного сервиса меняет его в `/etc/matching-engine/config.json` без пересборки.

Превышение — нарушение протокола, а не ошибка пользователя; последствия описаны в разделе 4.

### 1.2. Нулевой размер полезной нагрузки

**Решение: кадр с нулевой длиной корректен на уровне кадра и отвергается на уровне запроса.**

Кодек, разобрав заголовок с длиной 0, возвращает размер 0 и не считает это нарушением протокола: поток кадров остаётся синхронным — следующий кадр начинается сразу за заголовком, и позиция в потоке известна точно. Судить о содержимом полезной нагрузки кодек не вправе: для него это непрозрачные байты.

Дальше пустая строка попадает на разбор JSON, не является JSON-объектом и порождает обычный ответ со статусом `ERROR` и кодом `INVALID_REQUEST`. Соединение при этом живёт.

Такое разделение выбрано потому, что альтернатива — «нулевая длина есть нарушение протокола, соединение закрывается» — наказывает разрывом связи за ошибку, которая не мешает читать поток дальше. Закрытие соединения приберегается для случаев, когда продолжать чтение действительно нельзя (раздел 4).

### 1.3. Кодек

Вся работа с двоичным представлением собрана в одном компоненте — `MessageCodec` (`REQ-PROTO-04`). У него две операции:

- **кодирование**: строка полезной нагрузки → готовый кадр (заголовок в сетевом порядке + тело);
- **декодирование заголовка**: четыре байта → длина полезной нагрузки, с проверкой допустимости.

`htonl`, `ntohl`, `memcpy` по буферу кадра и любые другие манипуляции с байтами существуют только внутри кодека и не встречаются ни в сессии, ни в сервере, ни в клиенте (`REQ-PROTO-05`). Кодек не знает ни о сокетах, ни о Boost.Asio, ни о содержимом полезной нагрузки, и потому проверяется обычными unit-тестами без сети.

Кодек один и тот же на обеих сторонах: сервер и клиент пользуются им же, поэтому расхождение формата между ними невозможно по построению.

## 2. JSON запроса

Полезная нагрузка одного кадра — **ровно один** JSON-объект с одной командой. Пакет команд, который принимает консольная программа (`{"commands":[…]}`), в сетевом протоколе не используется: одна команда — один кадр — один ответ.

| Команда | Обязательные поля | Пример |
|---|---|---|
| `ADD` (лимитная) | `order_id`, `side`, `price`, `quantity`, `command_id` | `{"type":"ADD","order_id":1,"side":"BUY","price":100,"quantity":10,"command_id":"cmd-1001"}` |
| `ADD` (рыночная) | `order_id`, `side`, `quantity`, `order_type` со значением `MARKET`, `command_id` | `{"type":"ADD","order_type":"MARKET","order_id":7,"side":"SELL","quantity":5,"command_id":"cmd-1007"}` |
| `CANCEL` | `order_id`, `command_id` | `{"type":"CANCEL","order_id":1,"command_id":"cmd-55"}` |
| `MODIFY` | `order_id`, `price`, `quantity`, `command_id` | `{"type":"MODIFY","order_id":1,"price":101,"quantity":8,"command_id":"cmd-72"}` |
| `PRINT` | — | `{"type":"PRINT"}` |
| `PING` | — | `{"type":"PING"}` |
| `HEALTH` | — | `{"type":"HEALTH"}` |

Идентификатор заявки передаётся полем `order_id` (`REQ-API-10`). Имя `id`, которым пользуется консольный режим предыдущих работ, принимается как синоним: разбор команд понимает оба, значение одно и то же. Оба имени реальны — одно пришло из предыдущих работ вместе со своими тестами и документацией, другое задано сетевым API, — поэтому поддерживаются оба, а не выбрано одно ценой поломки другого.

Остальные поля команд предметной области унаследованы от предыдущей работы без изменений.

`ADD`, `CANCEL` и `MODIFY` изменяют состояние, поэтому требуют `command_id` — на нём держится идемпотентность (`REQ-API-01`, `REQ-API-02`). `PRINT`, `PING` и `HEALTH` состояние не меняют, в базу не пишутся и `command_id` не требуют (`REQ-API-05`, `REQ-EXT-07`); если клиент всё же прислал `command_id`, он возвращается в ответе эхом и ни на что не влияет.

**`PING` и `HEALTH` не проходят через разбор команд предметной области.** Это служебные команды транспортного уровня: у них нет `command_id`, они не идут в базу и не касаются книги заявок. Маршрутизация по полю `type` происходит до того, как запрос попадает в разбор команды.

`PRINT` тоже не идёт по пути изменяющих команд: он читает текущее состояние книги напрямую, как и в консольном режиме. Новое здесь только то, что состояние нужно сериализовать в JSON ответа, а не напечатать.

## 3. JSON ответа

На каждый запрос отправляется ровно один ответ, в таком же кадре.

### 3.1. Успешное выполнение изменяющей команды

```json
{
  "command_id": "cmd-1002",
  "status": "OK",
  "order_id": 2,
  "trades": [
    { "buy_order_id": 1, "sell_order_id": 2, "price": 100, "quantity": 7 }
  ]
}
```

Поле `trades` присутствует всегда и пусто, если сделок не было; `order_id` — идентификатор заявки, которой команда касалась (`REQ-API-03`). `command_id` возвращается эхом — клиент сопоставляет ответ со своим запросом.

### 3.2. `PING`

```json
{ "status": "OK", "result": "PONG" }
```

Формат задан требованием буквально (`REQ-API-04`) и не расширяется.

### 3.3. `HEALTH`

```json
{ "status": "OK", "database": "CONNECTED", "engine": "READY" }
```

Состояние сервиса, доступность подключения к базе и готовность движка (`REQ-EXT-06`). Формат задан требованием буквально и не расширяется — как и у `PING`. Команда ничего не изменяет: проверка базы выполняется чтением, книга не трогается.

### 3.4. `PRINT` — состояние книги заявок

Формат ответа на `PRINT` задания не касается, но без него не обойтись: восстановление книги после перезапуска проверяется именно этим ответом (`REQ-API-08`, `REQ-TEST-06`). Незафиксированный формат был бы придуман трижды — в сервере, в клиенте и в тесте, — и все три раза по-разному.

```json
{
  "status": "OK",
  "result": {
    "buy":  [ { "order_id": 1, "price": 100, "quantity": 3 } ],
    "sell": [ { "order_id": 5, "price": 101, "quantity": 10 },
              { "order_id": 6, "price": 102, "quantity": 4 } ]
  }
}
```

Заявка в снимке книги названа тем же полем `order_id`, что и в остальном API.

**Порядок элементов в массивах значим и является частью формата.** Заявки перечисляются в порядке приоритета исполнения: `buy` — по убыванию цены, `sell` — по возрастанию, внутри одного ценового уровня — в порядке поступления. Это прямое отображение Price-Time Priority, и именно порядок позволяет тесту убедиться, что после перезапуска восстановился не только состав книги, но и очерёдность внутри уровня.

Поле `quantity` — остаток заявки, а не исходный объём: книга хранит именно остаток, и частично исполненная заявка обязана вернуться из базы с ним же.

Номер последовательности в ответ не выносится: приоритет уже выражен порядком элементов, а его внутреннее представление — деталь хранения, которой API знать не обязан.

### 3.5. Ошибка

```json
{
  "command_id": "cmd-55",
  "status": "ERROR",
  "error": "ORDER_NOT_FOUND",
  "message": "Order 999999 does not exist"
}
```

`error` — код для программы, `message` — описание для человека; оба лежат на верхнем уровне объекта, вложенного объекта ошибки нет (`REQ-API-06`). `command_id` присутствует, если он был в запросе и запрос удалось разобрать настолько, чтобы его извлечь.

| Код | Когда | Что с соединением |
|---|---|---|
| `INVALID_REQUEST` | не JSON, нет обязательного поля, поле не того типа, неизвестный тип команды, пустая полезная нагрузка | живёт |
| `INVALID_ORDER` | значения не проходят проверку предметной области (неположительная цена или количество, неизвестная сторона) | живёт |
| `DUPLICATE_ORDER` | заявка с таким `id` уже есть в книге | живёт |
| `ORDER_NOT_FOUND` | `CANCEL` или `MODIFY` для несуществующей заявки | живёт |
| `MESSAGE_TOO_LARGE` | заявленный размер **запроса** больше `server.max_message_size` | закрывается после отправки ответа |
| `RESPONSE_TOO_LARGE` | запрос корректен, но **ответ** на него не помещается в `server.max_message_size` — например, `PRINT` при очень большой книге | живёт |
| `INTERNAL_ERROR` | сбой сохранения в базу | закрывается, сервис завершает работу |

`INTERNAL_ERROR` стоит особняком: если книга в памяти уже изменена, а запись в базу не удалась, состояние сервиса разошлось с хранилищем, и продолжать обслуживание нельзя. Это поведение унаследовано от предыдущей работы и в сети не смягчается — сервер отвечает клиенту и завершается, а не продолжает торговать по расходящимся данным.

Завершение при этом штатное, но **с кодом возврата 1**: соединения закрываются, ресурсы освобождаются, деструкторы отрабатывают — аварийного прерывания процесса нет, ненулевым остаётся только код. Различие существенно для системы инициализации: при политике перезапуска `Restart=on-failure` нулевой код означал бы, что сервис завершился по плану и перезапускать его не нужно, — то есть отказ базы тихо погасил бы сервис. Ненулевой код, наоборот, приводит к перезапуску, и это желаемое поведение: недоступная база может подняться, а восстановление книги при старте предусмотрено. От бесконечного цикла перезапусков при долго недоступной базе защищает ограничение частоты запусков; политика целиком описана в `03-systemd.md`.

### 3.6. Повтор команды с тем же `command_id`

Повторная команда возвращает **тот же ответ**, что и первое выполнение (`REQ-API-09`): тот же `status`, тот же список сделок. Признака «это был повтор» в ответе нет — требование говорит именно о совпадении ответов.

Здесь есть ловушка, которую документ фиксирует намеренно. В консольном режиме повтор `command_id` наружу отдавал пустоту: результат брался из кеша, но в отчёт не разворачивался. Механически перенести это поведение в сеть — значит вернуть на повтор `"trades": []` там, где первое выполнение вернуло сделку, и провалить требование. Ответ на повтор строится из сохранённого результата команды тем же сериализатором, что и ответ на первое выполнение.

### 3.7. Формат ответа и формат хранения — разные вещи

Ответ клиенту (`status`, `trades`, `error`) и запись результата команды в базе (`trades`, `order_changes`) описывают разное: первый — внешний интерфейс, вторая — способ восстановить эффект команды при перезапуске. Их сериализация выполняется разными функциями и по разным правилам.

Склеивание этих двух форматов в одну функцию дало бы либо утечку внутренних снимков заявок в API, либо порчу формата хранения при следующей же правке API. Имена полей сделки в них совпадают — это удобство читателя, а не общий код.

## 4. Граница между ошибкой протокола и ошибкой пользователя

Разделение простое и проходит по одному признаку: **можно ли после ошибки продолжать читать поток кадров.**

**Ошибка пользователя — соединение живёт.** Битый JSON, отсутствующее поле, неизвестный тип команды, несуществующая заявка, дубликат `id`, пустая полезная нагрузка. Во всех этих случаях кадр прочитан целиком и корректно, позиция в потоке известна, следующий кадр начинается там, где и должен. Сервер отвечает `status: ERROR` и продолжает читать из того же сокета (`REQ-API-07`). Сессия не закрывается, другие соединения не затрагиваются, сервер не завершается.

**Ошибка протокола — соединение закрывается.** Заявленный размер больше максимального (`REQ-PROTO-10`). Читать дальше невозможно: чтобы добраться до следующего кадра, пришлось бы вычитать и выбросить объявленное число байт, доверяя источнику, который контракт уже нарушил, — а объявить он мог 2 ГБ. Сервер отправляет один ответ с кодом `MESSAGE_TOO_LARGE` и закрывает соединение.

**Ошибка транспорта — соединение уже закрыто.** Клиент отключился, соединение сброшено, поток оборвался посреди кадра. Ответ отправлять некому; сессия освобождает ресурсы и завершается.

Смешение первых двух категорий — прямой провал `REQ-API-07`: если ошибочная команда рвёт соединение, клиент теряет связь из-за собственной опечатки, а при обслуживании нескольких клиентов ошибка одного начинает выглядеть как отказ сервиса.

### 4.1. Отдельный случай: не помещается ответ, а не запрос

Запрос может быть безупречным, а ответ на него — не влезать в `server.max_message_size`. Очевидный пример: `PRINT` при очень большой книге заявок.

**Это ошибка пользователя, а не протокола: соединение живёт.** Признак раздела 4 выполняется полностью — кадр запроса прочитан целиком, позиция в потоке известна, следующий кадр начинается там, где должен. Сервер отвечает коротким кадром с кодом `RESPONSE_TOO_LARGE` и продолжает читать из того же сокета.

Закрывать соединение здесь было бы наказанием клиента за размер ответа сервера. Ничто не мешает ему следующей командой запросить что-то поменьше.

**Из этого следует ограничение на конфигурацию.** Решение работает, только если короткий ответ об ошибке помещается в лимит всегда. Длина ответа об ошибке ограничена сверху константами (пользовательские фрагменты в нём усекаются), поэтому `server.max_message_size` имеет **нижнюю границу** — не меньше максимально возможного ответа об ошибке. Она проверяется при загрузке конфигурации: значение ниже границы делает сервис неспособным сообщить об ошибке вообще, и это отказ конфигурации, а не ситуация времени выполнения.

#### Изменяющая команда: команда выполнена, ответ не доставлен

Для `PRINT` случай безобиден — запрос можно повторить. Для успешно выполненной изменяющей команды всё иначе: заявка сопоставлена, сделки записаны, транзакция закоммичена — а ответ выброшен. Повтор с тем же `command_id` вернёт из кеша идемпотентности тот же самый негабаритный результат и ту же ошибку, поэтому список сделок клиенту недоступен и при повторе.

**Опаснее здесь не потеря списка сделок, а ложный вывод клиента.** `RESPONSE_TOO_LARGE` приходит со статусом `ERROR`; клиент, получивший ошибку на `ADD`, разумно заключит, что заявка не принята, и отправит её заново — уже **с новым `command_id`**. Идемпотентность от этого не защищает: она распознаёт повтор того же идентификатора, а не новую команду с тем же смыслом. Результат — дубль заявки и удвоенная позиция.

Поэтому в этом случае:

- поле `message` **обязано явно сообщать, что команда выполнена и сохранена**, а не доставлен только ответ. Это единственное, что отделяет клиента от ложного вывода;
- сервер записывает в журнал `command_id`, `order_id` и число сделок — результат остаётся восстановимым оператором из журнала и базы, даже если клиент его не увидел;
- соединение, как и в остальных случаях этого раздела, живёт.

Усечённый ответ — со статусом `OK`, но без массива сделок — сознательно **не вводится**: это новый формат, которого нет ни в задании, ни в остальном контракте, а достижимость случая мала. При лимите в 1 МБ одна команда должна породить порядка тринадцати тысяч сделок.

**Практический вывод для эксплуатации:** `max_message_size` не следует ставить близко к нижней границе. Значение по умолчанию в 1 МБ оставляет запас на тысячи сделок в одном ответе; нижняя граница гарантирует лишь доставку сообщения об ошибке, а не полезной работы.

## 5. `Server` и `Session`

```
Server                                  Session (по одной на соединение)
──────                                  ────────────────────────────────
владеет acceptor                        владеет своим сокетом
async_accept ──── создаёт ──────────►   читает 4 байта заголовка
принимает следующее соединение          читает N байт тела
ведёт реестр живых сессий               разбирает запрос, получает ответ
                                        ставит ответ в очередь записи
                                        читает следующий кадр
```

**`Server`** (`REQ-NET-08`) владеет `acceptor`, открывает приём на адресе и порту из конфигурации, сообщает о готовности строкой `Listening on <адрес>:<порт>` (`REQ-NET-13`) и ведёт реестр живых сессий, который нужен при остановке. Число одновременных соединений искусственно не ограничивается: каждое получает собственную `Session` (`REQ-EXT-01`).

Порядок запуска задан требованием `REQ-NET-14` и обратному не подлежит: подключение к PostgreSQL → восстановление книги заявок → прогрев кеша идемпотентности → и только затем начало прослушивания порта. Клиент, подключившийся к порту, должен попасть на готовый к работе движок, а не на процесс, который ещё поднимается.

**`Session`** (`REQ-NET-05`, `REQ-NET-06`) отвечает за один сокет: чтение заголовка, чтение тела, разбор запроса, отправку ответа и собственное время жизни.

Всё общение с сетью асинхронное — `async_accept`, `async_read`, `async_write` (`REQ-NET-03`). Цикла опроса вида `while (true) { if (socketHasData()) … }` в проекте нет (`REQ-NET-04`): между кадрами поток не крутится вхолостую, а обслуживает другие соединения.

Сетевой слой надстраивается над движком, не проникая внутрь: `MatchingEngine` и `OrderBook` не знают ни о сокетах, ни о Boost.Asio, ни о формате кадра (`REQ-NET-11`). Обратное тоже верно — `Session` не знает, как устроена книга заявок, и получает готовый ответ от вышележащего слоя.

### 5.1. Время жизни асинхронных операций

`Session` живёт в `std::shared_ptr` и наследует `std::enable_shared_from_this` (`REQ-NET-07`). Каждый асинхронный вызов захватывает `shared_from_this()` в свой обработчик завершения, поэтому:

- пока для сессии есть незавершённая операция, счётчик ссылок не нулевой, и объект не разрушается;
- когда клиент отключился и новых операций не запускается, последний обработчик отпускает ссылку, и деструктор закрывает сокет.

Это единственный механизм управления временем жизни соединения: явного удаления сессий нет, реестр в `Server` хранит слабые ссылки и на время жизни не влияет. Обработчик, продолжающий цепочку чтения, — единственное место, где ссылка передаётся дальше; ошибка в этом месте даёт либо обращение к разрушенному объекту, либо соединение, которое никогда не освобождается. Поэтому за захватом `shared_from_this()` в каждом асинхронном вызове следит ревью.

### 5.2. Обработка частичного чтения

Заголовок и тело читаются операцией чтения **точной длины**: сначала ровно 4 байта, затем ровно N. Такая операция завершается только тогда, когда затребованное число байт получено полностью, и сама дочитывает недостающее, если данные пришли частями. Лишнее, пришедшее сверх запрошенного, остаётся в буфере ядра и достаётся следующему чтению — поэтому несколько кадров, пришедших одним пакетом, обрабатываются один за другим (`REQ-PROTO-06`, `REQ-PROTO-07`).

Собственный накопительный буфер не заводится. Это решение принято сознательно, вместе с его последствием для тестов, — см. раздел 6.2.

### 5.3. Очередь записи

`Session` держит очередь готовых ответов. Новая асинхронная запись не начинается, пока не завершилась предыдущая на том же сокете (`REQ-NET-09`):

1. готовый ответ помещается в конец очереди;
2. если до этого очередь была пуста, запускается запись первого элемента;
3. по завершении записи элемент удаляется из начала очереди; если очередь не опустела, запускается запись следующего.

Так на сокете в любой момент активна не более чем одна операция записи, а ответы уходят строго в порядке поступления запросов. Без очереди два перекрывающихся `async_write` перемешали бы байты двух кадров, и клиент получил бы мусор, который не разберёт ни один кодек.

Очередь нужна именно потому, что чтение следующего кадра начинается сразу после постановки ответа в очередь, не дожидаясь его фактической отправки: при склейке нескольких кадров в одном пакете следующий ответ может быть готов раньше, чем ушёл предыдущий.

Ограничение очереди по длине не вводится: сервер отвечает ровно по одному кадру на запрос, а клиент, заваливающий сервер запросами и не читающий ответы, в учебном сценарии не рассматривается. Ограничение осознанное, а не забытое.

### 5.4. Обработка отключения клиента

Разрыв соединения — штатное событие, а не ошибка (`REQ-NET-10`). Операция чтения завершается признаком конца файла или сбросом соединения; сессия не запускает новых операций, освобождает ссылку на себя и разрушается вместе с сокетом. Исключение наружу не выпускается, цикл событий продолжает работу, остальные соединения не затрагиваются.

Отдельный случай — клиент, который подключился и молчит. Такое соединение не должно занимать ресурсы бесконечно, поэтому на чтение ставится таймаут (`REQ-EXT-04`, `REQ-EXT-05`): по его истечении сессия закрывается так же, как при отключении.

## 6. Тесты

### 6.1. Общие правила

Все сетевые тесты подчиняются четырём правилам, заданным требованиями `REQ-TEST-09`, `REQ-TEST-10`, `REQ-TEST-11`:

1. **Сервер поднимается внутри тестового процесса.** Иначе ThreadSanitizer не увидит взаимодействия потоков, а тест восстановления, которому нужно создать новый экземпляр сервера, невыполним в принципе.
2. **Порт выбирает операционная система** — сервер слушает `port = 0`, фактический номер узнаётся после привязки. Фиксированный номер в тесте означает конфликт при параллельном прогоне и ложное падение.
3. **Готовность сервера определяется синхронизацией**, а не ожиданием: `promise`/`future`, `condition_variable`, callback или обработчик завершения. Пауза фиксированной длины как способ дождаться готовности запрещена: на загруженной машине она короткая, а на быстрой — потраченное время.
4. **У каждого теста есть ограничение по времени**, и по его истечении тест падает, а не висит. Зависший тест не даёт ни результата, ни диагноза.

Клиентская часть тестов — тот же компонент, которым пользуется `matching-engine-client` (`REQ-CLI-04`, `REQ-TEST-02`): подключение, отправка кадра, приём кадра, разбор JSON. Отдельного тестового клиента не пишется — иначе тесты проверяли бы сами себя, а не протокол.

### 6.2. Обязательные сценарии

| Тест | Что проверяет | Требование |
|---|---|---|
| `PING` | ответ `{"status":"OK","result":"PONG"}` | `REQ-TEST-03` |
| `ADD` | `ADD BUY 100×10`, затем `ADD SELL 100×4`; в ответе на вторую команду есть сделка | `REQ-TEST-04` |
| Идемпотентность | одна команда с одним `command_id` отправлена дважды: сделок не прибавилось, книга не изменилась, второй ответ совпадает с первым | `REQ-TEST-05` |
| Восстановление | заявки добавлены, сервер остановлен, поднят новый экземпляр, новый клиент запрашивает `PRINT` — состав и порядок книги те же | `REQ-TEST-06` |
| Фрагментация | сообщение отправлено четырьмя частями: часть заголовка, остаток заголовка, часть тела, остаток тела | `REQ-TEST-07` |
| Склейка | три кадра отправлены одним вызовом записи, обработаны все три | `REQ-TEST-08` |
| Превышение размера | заголовок объявляет размер больше максимального: ответ с кодом ошибки, соединение закрыто, сервер жив | `REQ-PROTO-10` |
| Ошибка пользователя | битый JSON не разрывает соединение: следующая команда в том же соединении выполняется | `REQ-API-07` |

### 6.3. Чего тесты фрагментации и склейки на самом деле не проверяют

Это сказано прямо, потому что иначе выглядит как недосмотр.

Раз заголовок и тело читаются операцией точной длины (раздел 5.2), библиотека **сама** дочитывает недостающее и сама оставляет лишнее до следующего чтения. Собственной логики сборки кадра из кусков в проекте нет — и проверять в тестах фрагментации и склейки, строго говоря, нечего: они пройдут при любой реализации, построенной на чтении точной длины.

Их ценность в другом: они исключают наивную реализацию — ту, что читает «сколько пришло» и считает прочитанное целым сообщением. Но исключают её по-разному, и это различие пришлось установить проверкой, а не рассуждением.

**Тест фрагментации ловит наивное чтение, тест склейки — нет.** Подмена чтения точной длины на чтение «сколько пришло» роняет тест фрагментации и оставляет тест склейки зелёным; проверено прогонами, а не выведено из общих соображений. Причина в том, что операция чтения никогда не возвращает больше запрошенного: сессия просит ровно четыре байта заголовка, затем ровно N байт тела, и когда все три кадра уже лежат в приёмном буфере, наивное чтение возвращает столько же, сколько точное. Разница между ними проявляется только при **недо**доставке, то есть ровно в сценарии фрагментации.

Из этого не следует, что тест склейки бесполезен: он ловит свой класс дефекта — реализацию, которая обработает первый кадр из пришедшего пакета и потеряет остальные либо перепутает порядок ответов. Подтверждено инъекцией: сессия, перестающая читать следующий кадр после ответа, роняет его стабильно.

Отсюда способ убедиться, что тесты не декоративные, различается по тесту: для фрагментации — подмена чтения точной длины на чтение «сколько пришло»; для склейки — отказ читать следующий кадр после отправки ответа. Каждый обязан покраснеть на своей подмене; если остаётся зелёным, это находка, а не повод оставить как есть.

Выбор в пользу чтения точной длины сделан осознанно: собственный накопительный буфер — это больше кода и больше мест для ошибки того самого класса, который не воспроизводится детерминированно и потому дороже всего ловится.
