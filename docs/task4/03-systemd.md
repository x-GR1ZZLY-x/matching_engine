# Служба systemd

Документ фиксирует, каким образом `matching-engine-server` работает как служба Linux: содержимое unit-файла, пути установки, откуда берутся конфигурация и пароль, что происходит при остановке и перезапуске, куда идёт журнал и какими командами всё это проверяется.

Покрывает `REQ-DOC-09`. Как и предыдущие документы, он пишется **до** соответствующих файлов: unit-файл — это набор решений об эксплуатации, а не формальность, и большинство ошибок в нём проявляется не при сборке, а при первой установке на чужую машину.

Порядок остановки, коды возврата и предельное время описаны в `01-service-lifecycle.md` и здесь не пересматриваются — этот документ смотрит на них со стороны службы. Состав пакета и правила установки файлов — в `04-deb-package.md`.

---

## 1. Unit-файл

Файл `matching-engine.service` (`REQ-SYS-01`), в репозитории — `packaging/systemd/matching-engine.service`, в установленном виде — `/lib/systemd/system/matching-engine.service`.

```ini
[Unit]
Description=Matching Engine TCP service
After=network-online.target postgresql.service
Wants=network-online.target
StartLimitIntervalSec=300
StartLimitBurst=5

[Service]
Type=simple
ExecStart=/usr/bin/matching-engine-server --config /etc/matching-engine/config.json
EnvironmentFile=/etc/matching-engine/matching-engine.env

DynamicUser=yes

Restart=on-failure
RestartSec=5s
TimeoutStopSec=30

StandardOutput=journal
StandardError=journal
SyslogIdentifier=matching-engine

[Install]
WantedBy=multi-user.target
```

Одна деталь размещения стоит того, чтобы назвать её сразу: **ограничение частоты запусков задаётся не там, где задаётся сам перезапуск.** `Restart=` и `RestartSec=` живут в секции `[Service]`, а `StartLimitIntervalSec=` и `StartLimitBurst=` — в `[Unit]`. Написанные по соседству с `Restart=`, они молча не действуют: менеджер не считает неизвестные ключи ошибкой в той мере, чтобы это бросалось в глаза, и защита от цикла перезапусков оказывается выключенной при внешне правильном файле.

Разбор каждого решения — ниже.

## 2. Что запускается и как

### 2.1. `ExecStart` и аргументы

```
ExecStart=/usr/bin/matching-engine-server --config /etc/matching-engine/config.json
```

Путь к бинарнику абсолютный — systemd не выполняет поиск по `PATH` и не разворачивает переменные оболочки в `ExecStart`.

**Путь к конфигурации задан явно и не полагается на умолчание, встроенное в программу** (`REQ-CFG-01`). Так unit-файл остаётся самодостаточным: он сообщает, какой файл читает служба, не требуя знать поведение бинарника по умолчанию, и позволяет администратору переопределить путь в drop-in файле. Побочная выгода существеннее: служба продолжит читать нужный файл независимо от того, каким умолчание окажется в будущих версиях программы.

Никаких `sh -c`, конвейеров и перенаправлений в `ExecStart` нет: они потребовали бы оболочки как промежуточного процесса, а сигнал остановки уходил бы ей, а не сервису.

### 2.2. `Type=simple` и почему демонизации нет

Служба остаётся процессом переднего плана. Она не выполняет двойной `fork`, не вызывает `setsid`, не пишет pid-файл и не закрывает стандартные потоки.

Слово «демон» провоцирует ровно противоположное, поэтому сказано прямо: **классическая демонизация здесь не просто не нужна, а вредна.** При `Type=simple` менеджер служб считает главным процессом тот, который он запустил сам. Процесс, сделавший `fork` и завершивший родителя, немедленно выглядит для менеджера как завершившийся: служба будет объявлена упавшей, `SIGTERM` при остановке уйдёт по неверному адресу, а настоящий рабочий процесс останется жить сиротой. Отслеживание по контрольной группе спасает от полной потери процесса, но состояние службы всё равно перестаёт соответствовать действительности.

Готовность сервиса (`REQ-NET-13`) сообщается строкой журнала, а не уведомлением менеджеру. Вариант `Type=notify` рассматривался и отвергнут: он точнее — менеджер узнавал бы о готовности к приёму соединений в тот самый момент, когда открыт слушающий сокет, — но требует зависимости от библиотеки systemd в коде приложения ради одного вызова. Для учебного сервиса, у которого нет служб, зависящих от его готовности, цена выше пользы. Практическое следствие названо честно: `systemctl start` возвращает управление, когда процесс запущен, а не когда сервер начал слушать порт; между этими моментами лежит подключение к базе и восстановление книги заявок.

### 2.3. Рабочий каталог не задаётся

`WorkingDirectory=` в unit-файле отсутствует намеренно, и это решение, а не пропуск.

Служба, запущенная менеджером, получает рабочим каталогом корень файловой системы. Любой относительный путь внутри приложения при этом разрешается не туда, где лежали файлы при разработке. Раньше такой путь в проекте был — каталог со схемой базы задавался относительно корня репозитория; сейчас он является полем конфигурации `database.schema_dir`, и в установленном виде содержит абсолютный путь (`04-deb-package.md`, раздел 2).

Это и есть причина, по которой рабочий каталог не нужен: **у сервиса не осталось ни одного относительного пути**, и задавать `WorkingDirectory=` значило бы вернуть скрытую зависимость от каталога запуска, которую только что убрали. Решение записано здесь, чтобы следующая правка не «починила» его обратно.

## 3. От какого пользователя работает служба

Служба работает от **динамического системного пользователя**, который создаётся менеджером на время работы и исчезает вместе с ней:

```ini
DynamicUser=yes
```

От `root` служба не работает. Обоснование простое: сервису не нужны ни привилегированные порты (порт по умолчанию — 9000), ни доступ к чужим файлам, ни изменение системы. Единственная привилегированная операция во всём жизненном цикле — чтение файла с паролем, и она выполняется **менеджером** до запуска процесса (раздел 5).

### 3.1. Почему динамический пользователь, а не созданный при установке

Классическая альтернатива — завести системного пользователя сценарием установки пакета (`useradd --system matching-engine`) и указать его в `User=`. Она отвергнута, и вот чем платит:

| Свойство | Пользователь из сценария установки | `DynamicUser=yes` |
|---|---|---|
| Кто создаёт | сценарий `postinst` в пакете | менеджер служб при запуске |
| Что при удалении пакета | пользователь остаётся навсегда: удалять его опасно — им могут владеть оставшиеся файлы, и его идентификатор может быть переиспользован | ничего не остаётся: учётной записи не существует между запусками |
| Сопровождающие сценарии | нужны `postinst` и `postrm` в составе пакета | не нужны вовсе |
| Изоляция | задаётся отдельными настройками | включена по умолчанию: система только для чтения, домашние каталоги недоступны, `/tmp` приватный |

Второй строке стоит уделить внимание: осиротевшая учётная запись после удаления пакета — не теоретическая придирка, а причина, по которой рекомендации Debian требуют от сценариев удаления не трогать созданных пользователей. То есть аккуратно сделанный вариант с `useradd` **обязан** оставлять мусор в системе. Динамический пользователь снимает вопрос целиком и не требует ни одного сценария сопровождения.

### 3.2. Ограничение, которое нужно назвать

`DynamicUser=yes` означает, что идентификатор пользователя меняется между запусками. Отсюда два следствия, и оба существенны:

1. **Сервис не может владеть файлами на диске.** Ему это и не нужно — всё состояние живёт в PostgreSQL, а на диске он только читает конфигурацию и файлы схемы. Если в будущем сервису понадобится собственный каталог с данными, схема пользователя меняется целиком (`StateDirectory=` или обычный статический пользователь), а не дополняется.
2. **Аутентификация в PostgreSQL по имени системного пользователя невозможна.** Подключение выполняется по TCP с паролем, и метод `peer` через локальный сокет для этой службы неприменим в принципе: имени пользователя, под которым она работает, в базе нет и быть не может. Администратору, который захочет перевести подключение на локальный сокет с проверкой по системному имени, придётся отказаться от `DynamicUser=yes` — это записано здесь, чтобы обнаружение не пришлось на момент отладки отказа аутентификации.

Требует systemd версии 232 или новее; на всех поддерживаемых сегодня выпусках это выполнено.

## 4. Конфигурация

| Что | Путь | Кто правит |
|---|---|---|
| Основная конфигурация | `/etc/matching-engine/config.json` | администратор |
| Файл с паролем | `/etc/matching-engine/matching-engine.env` | администратор, вручную |
| Образец файла с паролем | `/etc/matching-engine/matching-engine.env.example` | поставляется пакетом |

Формат конфигурации — тот же единый формат, что и у остальных программ проекта: секция `server` с адресом, портом и максимальным размером сообщения и секция `database` с параметрами подключения (`REQ-CFG-02`). Устанавливаемый файл содержит нейтральные значения:

```json
{
    "server": {
        "address": "0.0.0.0",
        "port": 9000,
        "max_message_size": 1048576
    },
    "database": {
        "host": "127.0.0.1",
        "port": 5432,
        "name": "matching_engine_db",
        "user": "matching_engine_user",
        "schema_dir": "/usr/share/matching-engine/database"
    }
}
```

Значения выше — умолчания пакета, а не параметры какой-либо работающей установки: имя базы и пользователя администратор приводит в соответствие со своей средой при первой настройке.

**Пароля в этом файле нет и быть не может** (`REQ-CFG-03`). Приложение читает его только из переменной окружения `MATCHING_ENGINE_DB_PASSWORD` и отказывается стартовать, если она не задана. Разделение сделано ради того, чтобы конфигурацию можно было читать, показывать и хранить в системе управления конфигурациями, не задевая секрет.

Файл конфигурации объявлен файлом настроек пакета: правки администратора переживают обновление, а удаление пакета не сносит их молча (`REQ-PKG-12`). Механизм — в `04-deb-package.md`, раздел 3.

## 5. Файл с паролем

```ini
EnvironmentFile=/etc/matching-engine/matching-engine.env
```

Содержимое — одна строка (`REQ-CFG-04`):

```
MATCHING_ENGINE_DB_PASSWORD=<пароль роли базы данных>
```

| Свойство | Значение | Почему так |
|---|---|---|
| Владелец | `root:root` | файл читает менеджер служб, а не процесс сервиса |
| Права | `0600` | ни один непривилегированный пользователь не должен его прочитать |
| Кто создаёт | администратор вручную | пакет не знает и не может знать пароль |

**Установка пакета этот файл не создаёт** (`REQ-CFG-05`). Пакет поставляет только образец с пустым значением, а служба до создания настоящего файла не запустится: `EnvironmentFile=` без ведущего дефиса означает, что отсутствие файла — ошибка запуска. Это выбрано сознательно вместо мягкого варианта: служба, стартовавшая без пароля, всё равно немедленно упала бы на подключении к базе, но диагноз в журнале был бы менее прямым.

Порядок первой настройки:

```bash
sudo install -o root -g root -m 0600 /dev/null /etc/matching-engine/matching-engine.env
sudo sh -c 'echo "MATCHING_ENGINE_DB_PASSWORD=пароль" > /etc/matching-engine/matching-engine.env'
```

Права `0600` при `DynamicUser=yes` не мешают работе: `EnvironmentFile=` читается менеджером от имени `root` **до** того, как процесс переключится на динамического пользователя. Сам процесс файла не открывает — он получает уже готовое окружение. Этот порядок стоит помнить: попытка «исправить» права на более широкие, чтобы «сервис смог прочитать», ослабляет защиту, ничего не решая.

Пароль виден в окружении процесса, то есть доступен `root` и владельцу процесса через `/proc`. Для учебного сервиса это принято; в среде, где это неприемлемо, следующим шагом были бы средства хранения секретов менеджера служб, а не изменение файла.

## 6. Отношение к PostgreSQL

```ini
After=network-online.target postgresql.service
Wants=network-online.target
```

Ключевое здесь — то, чего **нет**: нет `Requires=postgresql.service`.

База может работать на другой машине, и жёсткая зависимость от локальной службы означала бы, что сервис не запускается там, где базы просто не установлено. Поэтому зависимость объявлена только как порядок запуска: если PostgreSQL на этой же машине есть, он стартует раньше; если его нет, `After=` c несуществующей службой не мешает ничему.

**`After=` не гарантирует готовности базы принимать подключения.** Служба базы считается запущенной, когда запущен её управляющий процесс, а восстановление после сбоя, ожидание подключений или медленный старт кластера продолжаются и после этого. То есть окно «сервис стартовал раньше, чем база готова» остаётся открытым при любом наборе зависимостей.

Что при этом происходит: подключение не удаётся, сервис пишет причину в журнал и завершается с ненулевым кодом (`01-service-lifecycle.md`, раздел 4.4). Дальше вступает политика перезапуска — именно она, а не зависимости, является настоящей защитой от гонки при старте системы. Это осознанное разделение: зависимости выражают намерение, повторные попытки обеспечивают результат.

## 7. Перезапуск и защита от цикла

```ini
Restart=on-failure
RestartSec=5s
StartLimitIntervalSec=300
StartLimitBurst=5
```

`Restart=on-failure` требуется заданием (`REQ-SYS-07`) и означает: перезапускать, если процесс завершился с ненулевым кодом или был убит сигналом, и **не** перезапускать, если он завершился с кодом 0. Отсюда прямая связь с кодами возврата: любой отказ, из-за которого сервис прекратил работу сам, обязан давать ненулевой код — иначе служба тихо погаснет и останется погашенной. Полный перечень кодов — в `01-service-lifecycle.md`, раздел 4.4.

**Сам по себе `Restart=on-failure` даёт бесконечный цикл**, и это главное, ради чего написан раздел. Сценарий: база недоступна, сервис поднимается, не может подключиться, выходит с кодом 1, менеджер поднимает его снова — и так без конца, с той частотой, которую позволит скорость старта. Журнал за минуты заполняется одинаковыми сообщениями, а настоящая причина тонет в повторах.

Две настройки закрывают это:

| Настройка | Значение | Что делает |
|---|---|---|
| `RestartSec=5s` | 5 секунд | пауза перед повторным запуском: цикл перестаёт быть плотным, а кратковременная недоступность базы переживается без вмешательства |
| `StartLimitIntervalSec=300` / `StartLimitBurst=5` | 5 попыток за 5 минут | ограничение частоты: после пятой неудачной попытки в пределах окна менеджер прекращает попытки |

Пять попыток по пять секунд покрывают примерно полминуты недоступности базы — этого хватает на её перезапуск или на завершение восстановления после сбоя, но не растягивается настолько, чтобы отказ остался незамеченным.

**Что происходит, когда лимит исчерпан.** Служба переходит в состояние `failed` и больше не поднимается сама — в том числе не поднимется по `systemctl start`, пока счётчик не сброшен:

```bash
systemctl status matching-engine     # Active: failed (Result: exit-code)
sudo systemctl reset-failed matching-engine
sudo systemctl start matching-engine
```

**Причину прекращения попыток показывает журнал, а не поле состояния.** В строке `Result:` остаётся `exit-code` — то есть причина последнего завершения процесса, — а сработавшее ограничение частоты видно отдельной строкой журнала:

```
matching-engine.service: Scheduled restart job, restart counter is at 5.
matching-engine.service: Start request repeated too quickly.
```

Различие стоит знать заранее: администратор, ищущий в состоянии службы слово `start-limit`, его там не найдёт и решит, что ограничение не сработало, — тогда как процесс к этому моменту уже не запускается вовсе.

Необходимость `reset-failed` выглядит неожиданной ровно один раз, поэтому она названа здесь: без этой строки администратор решит, что служба сломана глубже, чем на самом деле. Проверено на живой службе: попытка `systemctl start` при уже исправленной конфигурации отказывает с той же строкой `Start request repeated too quickly`, не запуская процесс, и проходит только после сброса счётчика.

**Явная остановка перезапуска не вызывает** (`REQ-SYS-08`). Служба, остановленная командой `systemctl stop`, остаётся остановленной независимо от кода возврата процесса: политика `Restart=` не применяется к остановке, запрошенной оператором. Это относится и к принудительному завершению по истечении предельного времени — оно даёт ненулевой код, но перезапуска не будет, потому что остановку запросил администратор.

## 8. Остановка

`systemctl stop matching-engine` посылает главному процессу `SIGTERM` (`REQ-SYS-05`). Дальше работает механизм, описанный в `01-service-lifecycle.md`, раздел 4: сигнальный поток просыпается на `sigwait`, передаёт запрос остановки в цикл событий, сервер закрывает приём новых подключений, дозавершает начатые команды, отправляет накопленные ответы и закрывается, после чего процесс завершается с кодом 0.

Ни `KillMode`, ни `ExecStop` в unit-файле не заданы намеренно. Умолчания уже описывают нужное поведение: `SIGTERM` главному процессу, а по истечении отведённого времени — `SIGKILL` всей контрольной группе. Отдельная команда остановки не нужна — сервис умеет останавливаться по сигналу, и это его собственный механизм, а не внешний.

### 8.1. Согласование двух ограничений времени

| Ограничение | Значение | Где задано |
|---|---|---|
| Предельное время остановки приложения | **10 секунд** | константа в коде сервера (`01-service-lifecycle.md`, раздел 4.3) |
| Ограничение времени остановки со стороны службы | **30 секунд** | `TimeoutStopSec=30` в unit-файле (`REQ-SYS-09`) |

**Ограничение службы обязано быть строго больше прикладного**, и это не запас «на всякий случай», а условие работоспособности. Если бы `TimeoutStopSec=` был меньше или равен десяти секундам, `SIGKILL` приходил бы раньше, чем срабатывает собственный таймер сервиса: весь код принудительного, но корректного завершения оказался бы недостижим, а любая затянувшаяся остановка выглядела бы как убитый процесс.

Тройной запас выбран так, чтобы между двумя сроками помещалось всё, что происходит до начала остановки.

**Оговорка, без которой запас понимается неверно.** `TimeoutStopSec=` отсчитывается от посылки `SIGTERM`, а не от момента, когда приложение начало останавливаться. Сигнал, пришедший во время восстановления книги заявок, ждёт своей очереди: маска сигналов установлена, обработать его некому до запуска сигнального потока, и сервис сначала дозапускается, а потом останавливается. Эти секунды тратятся из тех же тридцати. Следствие: при книге, восстановление которой занимает больше примерно двадцати секунд, `SIGKILL` придёт посреди старта. Данных это не теряет — при восстановлении база только читается, — но остановка перестаёт быть корректной, и администратору такой установки следует увеличить `TimeoutStopSec=` через drop-in файл:

```bash
sudo systemctl edit matching-engine
```

```ini
[Service]
TimeoutStopSec=120
```

### 8.2. Перезапуск

`systemctl restart matching-engine` — это остановка и запуск, выполненные последовательно (`REQ-SYS-04`): старому процессу посылается `SIGTERM`, менеджер дожидается его завершения, и только затем запускает новый. Новый процесс проходит обычный порядок старта и восстанавливает книгу заявок из PostgreSQL (`REQ-COMPAT-03`) — состояние переживает перезапуск, потому что оно никогда и не жило только в памяти.

Перекрытия двух процессов не происходит: порт освобождается вместе с завершением старого, и новый занимает его без конфликта.

## 9. Журнал

Оба стандартных потока процесса отданы под диагностику и собираются менеджером (`REQ-SYS-06`):

```ini
StandardOutput=journal
StandardError=journal
SyslogIdentifier=matching-engine
```

В серверном режиме `std::cout` не используется вовсе: результат работы уходит клиенту в сокет, а диагностика идёт через журнал приложения, который пишет в стандартный поток ошибок. Обе настройки соответствуют умолчаниям современных версий менеджера и записаны явно, чтобы поведение не зависело от версии.

**Файлов журнала сервис не пишет и ротацией не занимается.** Это не упрощение, а следствие модели: собранные менеджером потоки уже попадают в системный журнал с ротацией, ограничением объёма, отметками времени и фильтрацией по службе. Собственный файл добавил бы вторую копию тех же строк и вторую же задачу по её обслуживанию.

Что видно в журнале при штатном цикле работы:

```
matching-engine[1234]: Connected to database
matching-engine[1234]: Schema applied
matching-engine[1234]: Recovered 128 active orders
matching-engine[1234]: Idempotency cache warmed up: 340 commands
matching-engine[1234]: Listening on 0.0.0.0:9000
matching-engine[1234]: Client connected: 127.0.0.1:52134
matching-engine[1234]: Received SIGTERM, starting shutdown
matching-engine[1234]: Stopping server: closing acceptor and draining sessions
matching-engine[1234]: Event loop stopped
matching-engine[1234]: Server stopped
```

Числа в примере условны. Существенна последовательность: она отражает обязательный порядок старта (`REQ-NET-14`) — подключение к базе, применение схемы, восстановление книги, прогрев кеша идемпотентности и только затем начало прослушивания порта. По этим строкам порядок и проверяется: строка о прослушивании, оказавшаяся раньше строки о восстановлении, означала бы, что клиент может попасть на неготовый сервер.

## 10. Пути установки

| Что | Путь |
|---|---|
| Сервер | `/usr/bin/matching-engine-server` |
| Клиент | `/usr/bin/matching-engine-client` |
| Конфигурация | `/etc/matching-engine/config.json` |
| Образец файла с паролем | `/etc/matching-engine/matching-engine.env.example` |
| Файл с паролем | `/etc/matching-engine/matching-engine.env` (создаёт администратор) |
| Файлы схемы базы | `/usr/share/matching-engine/database/` |
| Unit-файл | `/lib/systemd/system/matching-engine.service` |

Unit-файл ставится в каталог для файлов, принадлежащих пакетам; каталог `/etc/systemd/system/` остаётся администратору — туда попадают его собственные drop-in файлы, и обновление пакета их не касается. Разделение существенно: unit-файл, установленный пакетом в `/etc`, при следующем обновлении породил бы конфликт правок ровно там, где администратор ожидает свободы.

Полный состав пакета и способ, которым эти файлы туда попадают, — в `04-deb-package.md`.

## 11. Команды проверки

Установка unit-файла в систему и управление службой требуют прав администратора.

**Первый запуск после установки пакета:**

```bash
sudo systemctl daemon-reload                       # перечитать unit-файлы (REQ-SYS-02)
sudo systemctl start matching-engine               # запустить службу
systemctl status matching-engine                   # ожидается: Active: active (running) (REQ-SYS-03)
```

`daemon-reload` нужен после установки или изменения unit-файла: менеджер держит разобранные описания служб в памяти и сам файловую систему не перечитывает.

**Автозапуск при загрузке системы:**

```bash
sudo systemctl enable matching-engine              # создать ссылку из multi-user.target
sudo systemctl enable --now matching-engine        # то же плюс немедленный запуск
```

**Журнал:**

```bash
journalctl -u matching-engine                      # весь журнал службы (REQ-SYS-06)
journalctl -u matching-engine -f                   # следить за новыми строками
journalctl -u matching-engine -b                   # только с последней загрузки системы
journalctl -u matching-engine --since "10 min ago"
```

**Остановка и перезапуск:**

```bash
sudo systemctl stop matching-engine                # SIGTERM и graceful shutdown (REQ-SYS-05)
sudo systemctl restart matching-engine             # остановка, ожидание, запуск (REQ-SYS-04)
systemctl is-active matching-engine                # inactive после остановки
```

**Проверка того, что после явной остановки служба не поднимается сама** (`REQ-SYS-08`): выполнить `systemctl stop`, затем убедиться, что `systemctl is-active` продолжает отвечать `inactive`, а в журнале нет новых строк о старте.

**Проверка работы сервиса как такового** — тем же клиентом, который поставляется пакетом:

```bash
matching-engine-client --host 127.0.0.1 --port 9000
```

Команда `{"type":"PING"}` должна дать `{"status":"OK","result":"PONG"}`, команда `{"type":"HEALTH"}` — ответ с состоянием базы и движка.
