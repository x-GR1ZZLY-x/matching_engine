# Пакет .deb

Документ фиксирует, как проект попадает на чужую машину: правила установки в CMake, состав пакета и пути установки, настройки CPack и метаданные, определение зависимостей, откуда берётся версия, и что происходит при установке, обновлении и удалении.

Покрывает `REQ-DOC-10`. Пишется до самих правил установки — состав пакета и судьба конфигурации при обновлении относятся к тем решениям, которые дороже всего менять после того, как пакет уже кем-то установлен.

Unit-файл, права на файл с паролем и команды управления службой — в `03-systemd.md`; пути установки согласованы с его разделом 10 и повторены здесь как единый список.

---

## 1. Правила установки в CMake

Установка описывается вызовами `install()` (`REQ-PKG-01`), и на них же затем опирается CPack: пакет собирается не из отдельного списка файлов, а из того же дерева установки, которое даёт `cmake --install`. Это существенно — иначе состав пакета и результат ручной установки расходятся при первой же правке.

Каталоги берутся из стандартного модуля `GNUInstallDirs`, а не пишутся строками:

```cmake
include(GNUInstallDirs)

install(TARGETS matching-engine-server matching-engine-client
        RUNTIME DESTINATION ${CMAKE_INSTALL_BINDIR})

install(DIRECTORY database/
        DESTINATION ${CMAKE_INSTALL_DATADIR}/matching-engine/database)

install(FILES packaging/config/config.json
        DESTINATION ${CMAKE_INSTALL_FULL_SYSCONFDIR}/matching-engine)

install(FILES packaging/config/matching-engine.env.example
        DESTINATION ${CMAKE_INSTALL_FULL_SYSCONFDIR}/matching-engine)

install(FILES packaging/systemd/matching-engine.service
        DESTINATION /lib/systemd/system)
```

**Для конфигурации используется `FULL`-вариант переменной, и это не стилистическая мелочь.** Стандарт требует, чтобы при префиксе установки `/usr` конфигурация оказывалась в `/etc`, а не в `/usr/etc`. Модуль это правило соблюдает, но применяет его **только при вычислении `CMAKE_INSTALL_FULL_SYSCONFDIR`**: сама `CMAKE_INSTALL_SYSCONFDIR` при любом префиксе остаётся относительным значением `etc`, и правило установки с ней разложило бы файлы в `/usr/etc/matching-engine` — каталог, в который не заглядывает ни один администратор и который не совпадает с путём из unit-файла. Ошибка тихая: сборка проходит, пакет собирается, служба не находит конфигурацию только при запуске.

То же исключение действует для каталогов изменяемого состояния и файлов времени выполнения; для остальных каталогов (`BINDIR`, `DATADIR`) относительная форма верна и используется выше.

Каталог unit-файлов задан абсолютным путём сознательно: он не выводится из префикса установки и определяется менеджером служб, а не соглашениями об именовании каталогов.

Проверка ручной установкой, без сборки пакета:

```bash
cmake -B build -DCMAKE_INSTALL_PREFIX=/usr
cmake --build build -j$(nproc)
DESTDIR=/tmp/stage cmake --install build     # разложить в отдельный каталог и осмотреть
find /tmp/stage -type f | sort
```

**Перенаправление выполняется через `DESTDIR`, а не через `--prefix`, и заменить одно другим здесь нельзя.** Часть путей в правилах установки абсолютна — конфигурация в `/etc` и unit-файл в `/lib/systemd/system`; `--prefix` переопределяет только пути, вычисляемые от префикса, поэтому абсолютные ушли бы в настоящие системные каталоги. На машине без прав администратора это выглядит как отказ по правам посреди установки, а с правами — как молчаливая установка мимо временного каталога.

## 2. Состав пакета и пути установки

| Что | Путь установки | Требование |
|---|---|---|
| Сервер | `/usr/bin/matching-engine-server` | `REQ-PKG-04` |
| Клиент | `/usr/bin/matching-engine-client` | `REQ-PKG-05` |
| Конфигурация | `/etc/matching-engine/config.json` | `REQ-PKG-06`, `REQ-CFG-01` |
| Образец файла с паролем | `/etc/matching-engine/matching-engine.env.example` | `REQ-CFG-05` |
| Файлы схемы базы | `/usr/share/matching-engine/database/` | см. ниже |
| Unit-файл | `/lib/systemd/system/matching-engine.service` | `REQ-PKG-07`, `REQ-SYS-01` |

**Схема базы данных — тот элемент состава, которого нет в перечне требований, но без которого сервис не работает.** Приложение применяет схему при старте и берёт путь к ней из поля конфигурации `database.schema_dir`. В дереве разработки там лежит `database`, то есть путь относительно корня репозитория; для установленной службы такой путь бессмыслен — рабочим каталогом службы является корень файловой системы (`03-systemd.md`, раздел 2.3).

Поэтому место названо один раз и в одном виде: **`/usr/share/matching-engine/database/`**. Ровно это значение записано в поле `database.schema_dir` устанавливаемого файла конфигурации, и ровно туда `install(DIRECTORY ...)` кладёт файлы схемы. Два места, где путь мог бы разъехаться, — правило установки и файл конфигурации, — и оба заполняются из этого раздела; расхождение между ними проявилось бы только при первом запуске установленной службы, то есть на демонстрации.

Каталог выбран по назначению: файлы схемы не зависят от архитектуры, не правятся администратором и принадлежат пакету — это в точности содержимое `/usr/share`. Помещать их в `/etc` было бы ошибкой: администратор счёл бы их своими и стал бы править, а обновление пакета вступило бы с ним в конфликт.

**Старый консольный бинарник `matching_engine` в пакет не входит**, и это решение, а не пропуск. Он сохраняется в сборке, потому что на нём держится часть существующих тестов — пакетный режим обработки команд и прогон файла нагрузки; удаление бинарника ослабило бы проверенную базовую линию. Но службе он не нужен: она состоит из сервера и клиента, а режим разовой обработки команд к эксплуатации отношения не имеет. Правило `install(TARGETS ...)` перечисляет две цели из трёх именно поэтому.

## 3. Конфигурация как файл настроек

`/etc/matching-engine/config.json` правится администратором — там оказываются реальный адрес базы, имя роли и, возможно, другой порт. Из этого следуют два обязательства (`REQ-PKG-12`):

1. **Обновление пакета не затирает правки.** Новая версия не должна молча заменить файл своим умолчанием.
2. **Удаление пакета не сносит файл молча.** Правки администратора переживают удаление и восстанавливаются при повторной установке; окончательно файл убирается только полной очисткой.

Механизм Debian для этого — объявление файла в списке `conffiles`. Тогда при обновлении сравниваются три состояния: файл из старой версии пакета, файл из новой и текущий на диске. Если администратор файл не трогал, он обновляется молча; если трогал, а в пакете он изменился, у администратора спрашивают, что делать, и показывают разницу.

**CPack не делает этого сам** — модуль сборки DEB-пакетов помещает файлы туда, куда сказано, но списка `conffiles` не составляет, в том числе для содержимого `/etc`. Инструменты сборки Debian-пакетов, к которым привыкли, помечают такие файлы автоматически, и это несовпадение поведения — готовый источник ошибки: пакет выглядит правильным, а правки администратора исчезают при первом же обновлении.

Список составляется вручную и передаётся CPack как дополнительный управляющий файл:

```
packaging/debian/conffiles
```

```
/etc/matching-engine/config.json
```

```cmake
set(CPACK_DEBIAN_PACKAGE_CONTROL_EXTRA
    "${CMAKE_SOURCE_DIR}/packaging/debian/conffiles")
```

Образец файла с паролем (`matching-engine.env.example`) в список не входит: он не предназначен для правки на месте — администратор создаёт по нему отдельный файл (`03-systemd.md`, раздел 5), а сам образец обновляется вместе с пакетом.

Как проверить, что пометка сработала:

```bash
dpkg-deb --info matching-engine_1.0.0_amd64.deb          # раздел conffiles в выводе
dpkg-query --showformat='${Conffiles}\n' -W matching-engine   # после установки
```

Проверка по существу, а не по объявлению: изменить установленный `config.json`, установить пакет заново и убедиться, что правка на месте.

## 4. Версия

Версия задаётся **в одном месте** — в объявлении проекта:

```cmake
project(matching_engine VERSION 1.0.0 LANGUAGES CXX)
```

Оттуда она попадает и в метаданные пакета, и в имя файла: CPack берёт версию проекта, если ей не задано другое значение. Собственной переменной с версией пакета в конфигурации нет, и это главное требование к решению (`REQ-PKG-09`): два числа в двух местах разъезжаются при первом же изменении, причём молча — пакет соберётся, установится и будет неверно назван.

Версия `1.0.0` соответствует первому выпуску, пригодному к установке: сервис работает как служба, ставится пакетом и переживает перезапуск. Дальнейшая нумерация — обычная семантическая: несовместимые изменения протокола или формата конфигурации меняют старшее число, новые команды — среднее, исправления — младшее.

Имя файла пакета (`REQ-PKG-03`) складывается по правилам Debian из имени, версии и архитектуры:

```
matching-engine_1.0.0_amd64.deb
```

Такое имя CPack даёт при явном указании:

```cmake
set(CPACK_DEBIAN_FILE_NAME DEB-DEFAULT)
```

Без этой строки имя формируется по правилам CPack, а не Debian, и содержит имя проекта с версией в другом порядке — то есть требование к имени файла не выполняется при полностью правильном содержимом пакета.

## 5. Метаданные и настройки CPack

```cmake
set(CPACK_GENERATOR "DEB")
set(CPACK_PACKAGE_NAME "matching-engine")
set(CPACK_PACKAGE_DESCRIPTION_SUMMARY "Order matching engine TCP service")
set(CPACK_PACKAGE_CONTACT "Matching Engine maintainer <maintainer@example.com>")
set(CPACK_DEBIAN_PACKAGE_SECTION "misc")
set(CPACK_DEBIAN_PACKAGE_ARCHITECTURE "amd64")
set(CPACK_DEBIAN_PACKAGE_SHLIBDEPS ON)
set(CPACK_DEBIAN_FILE_NAME DEB-DEFAULT)

include(CPack)
```

| Метаданные | Значение | Откуда |
|---|---|---|
| Имя | `matching-engine` | задано явно; отличается от имени проекта в CMake (`matching_engine`), потому что дефис — соглашение об именовании пакетов, а подчёркивание в имени пакета Debian недопустимо |
| Версия | `1.0.0` | из объявления проекта, раздел 4 |
| Архитектура | `amd64` | сборка содержит машинный код |
| Сопровождающий | адрес из `CPACK_PACKAGE_CONTACT` | обязательное поле; без него сборка пакета завершается ошибкой |
| Описание | краткое и развёрнутое | обязательное поле |
| Раздел | `misc` | сервис не относится ни к одному специализированному разделу |

Эти поля закрывают `REQ-PKG-08`. Расхождение имён (`matching_engine` в CMake, `matching-engine` в пакете) названо явно, чтобы не выглядело опечаткой: имя цели сборки и имя пакета — разные сущности с разными правилами, и приводить их к одному виду не нужно.

**`include(CPack)` идёт последней строкой конфигурации**, после всех переменных: модуль читает их в момент подключения, и переменная, заданная после него, не попадёт в пакет — снова молча.

## 6. Зависимости

Зависимости определяются автоматически (`CPACK_DEBIAN_PACKAGE_SHLIBDEPS ON`): CPack просматривает установленные бинарники, находит библиотеки, с которыми они скомпонованы, и по ним определяет пакеты и минимальные версии.

Ручной список отвергнут по одной причине: он верен ровно в момент написания. Смена версии PostgreSQL, компилятора или дистрибутива сборки меняет набор и версии библиотек, а записанный руками список этого не заметит — пакет установится и не запустится.

Что попадает в зависимости фактически, видно по компоновке сервера: библиотека клиента PostgreSQL (`libpq`), стандартная библиотека C++, библиотека поддержки компилятора и системная библиотека C. Транзитивно за `libpq` приходят библиотеки шифрования и аутентификации.

**Boost в зависимостях не появляется, и это ожидаемо.** Используемая часть Boost.Asio — только заголовочные файлы, компоновки с библиотекой Boost не происходит; проверено при подключении и подтверждается тем, что в списке связанных библиотек её нет. Появление Boost в зависимостях пакета означало бы, что в проект попал компонент Boost, требующий компоновки, — то есть было бы поводом разобраться, а не поправить список.

Проверка после сборки пакета:

```bash
dpkg-deb --field matching-engine_1.0.0_amd64.deb Depends
```

Автоматическое определение требует пакета `dpkg-dev` на машине сборки. Это зависимость сборки, а не пакета: на машине, куда пакет устанавливается, она не нужна.

## 7. Сборка пакета

```bash
cmake -B build -DCMAKE_INSTALL_PREFIX=/usr
cmake --build build -j$(nproc)
cd build && cpack -G DEB
```

Результат — `build/matching-engine_1.0.0_amd64.deb` (`REQ-PKG-02`).

Префикс `/usr` задаётся при конфигурации и существен: он определяет, что бинарники окажутся в `/usr/bin`, а данные — в `/usr/share`. С умолчанием `/usr/local` пакет собрался бы тоже, но разложил бы файлы в каталоги, предназначенные для программ, установленных администратором вручную, — а пакет по определению устанавливается не вручную.

Сборка пакета прав администратора не требует. Права нужны только для установки.

### 7.1. Каталог сборки обязан лежать на файловой системе, сохраняющей права

Права файлов в пакете берутся из промежуточного каталога, который CPack создаёт внутри каталога сборки. Отсюда требование, не очевидное до первой проверки: **каталог сборки должен находиться на файловой системе, где действует смена прав доступа.**

Файловые системы, подключённые из другой операционной системы, этому условию не удовлетворяют: смена прав на них молча не выполняется, и любой файл виден как доступный всем на чтение, запись и исполнение. Пакет, собранный в таком каталоге, разложит по системе файлы с правами `rwxrwxrwx` — конфигурацию службы в `/etc` сможет переписать любой пользователь, а исполняемые файлы в `/usr/bin` — любой пользователь заменить своими. Ни сборка, ни установка при этом ни на что не пожалуются.

Проверить свойство файловой системы можно до сборки:

```bash
touch /path/to/build/probe && chmod 644 /path/to/build/probe
stat -c '%a' /path/to/build/probe     # 644 — годится, 777 — права не сохраняются
```

Проверить результат — после сборки, и это надёжнее:

```bash
dpkg -c matching-engine_1.0.0_amd64.deb
```

Ожидается `-rw-r--r--` у конфигурации, образца, unit-файла и файлов схемы, `-rwxr-xr-x` у двух исполняемых файлов и каталогов. Права `rwxrwxrwx` в этом выводе означают, что каталог сборки выбран неудачно; лечится сборкой в каталоге на обычной файловой системе, а не правкой правил установки — умолчания CMake дают верные права сами, и задавать их явно не нужно.

## 8. Установка, обновление и удаление

### 8.1. Установка

```bash
sudo apt install ./matching-engine_1.0.0_amd64.deb
```

Форма с `apt` и путём, начинающимся с `./`, предпочтительнее `dpkg -i`: `apt` доустановит недостающие зависимости сам, тогда как `dpkg` оставит пакет в состоянии неудовлетворённых зависимостей и потребует отдельной команды.

После установки доступны обе программы (`REQ-PKG-10`):

```bash
matching-engine-server --help
matching-engine-client --host 127.0.0.1 --port 9000
```

**Служба после установки не запускается сама, и это решение.** Сценариев сопровождения в пакете нет вовсе — ни создания пользователя (он динамический, `03-systemd.md`, раздел 3), ни перезагрузки конфигурации менеджера, ни автозапуска.

Причина прямая: запуск сразу после установки был бы **гарантированным падением**. Служба требует файла с паролем, которого пакет не создаёт и не может создать (`REQ-CFG-05`), и не знает параметров базы, которые администратор ещё не вписал. Автозапуск в такой ситуации дал бы упавшую службу и серию сообщений об ошибке в журнале в качестве первого впечатления от установки.

Поэтому порядок первого запуска — осознанно ручной:

```bash
sudo systemctl daemon-reload                      # перечитать unit-файл (REQ-SYS-02)
sudoedit /etc/matching-engine/config.json         # параметры базы
                                                  # создать файл с паролем (03-systemd.md, раздел 5)
sudo systemctl enable --now matching-engine
```

Первая строка нужна потому, что перезагрузку конфигурации менеджера не делает никто другой: без сценария сопровождения в пакете это работа администратора, и она названа в документе, а не оставлена на догадку.

### 8.2. Обновление

```bash
sudo apt install ./matching-engine_1.1.0_amd64.deb
```

Что происходит: бинарники, файлы схемы и unit-файл заменяются новыми; `config.json` сохраняет правки администратора (раздел 3); файл с паролем не затрагивается вовсе, поскольку пакету не принадлежит.

Работающая служба при этом **не перезапускается сама** — по той же причине, по которой не запускается после установки: сценариев сопровождения нет. До перезапуска в памяти продолжает работать старый бинарник:

```bash
sudo systemctl daemon-reload
sudo systemctl restart matching-engine
```

Перезапуск безопасен для данных: старый процесс останавливается gracefully, новый восстанавливает книгу заявок из базы (`REQ-COMPAT-03`).

### 8.3. Удаление

Два уровня, и разница между ними существенна:

```bash
sudo apt remove matching-engine     # удалить программу, сохранить конфигурацию
sudo apt purge matching-engine      # удалить вместе с конфигурацией
```

| Что | `remove` | `purge` |
|---|---|---|
| Бинарники, схема, unit-файл | удаляются | удаляются |
| `/etc/matching-engine/config.json` | **остаётся** (файл настроек) | удаляется |
| `/etc/matching-engine/matching-engine.env` | **остаётся** | **остаётся** |
| Данные в PostgreSQL | не затрагиваются | не затрагиваются |
| Системный пользователь | не создавался, удалять нечего | не создавался, удалять нечего |

**Файл с паролем не удаляется ни при каком варианте — и это правильно.** Он пакету не принадлежит: его создал администратор, и содержит он секрет, который может использоваться не только этой службой. Удалять чужой файл с чужим паролем пакет не вправе; администратор, желающий убрать его, делает это сам:

```bash
sudo rm /etc/matching-engine/matching-engine.env
sudo rmdir /etc/matching-engine                    # если каталог опустел
```

**Данные в базе тоже не удаляются.** Пакет не создаёт базу и не заводит роль — он только применяет схему при старте сервиса. Удаление пакета не должно уничтожать заявки и сделки, и не уничтожает; очистка базы — отдельное осознанное действие администратора.

Остановить службу перед удалением не требуется: это делается автоматически при удалении пакета, чей unit-файл исчезает.

## 9. Проверка состава пакета

Два разных вопроса требуют двух разных команд, и путать их не стоит: одна отвечает, что лежит **в файле пакета**, другая — что было **установлено в систему**.

**До установки, по самому файлу:**

```bash
dpkg -c matching-engine_1.0.0_amd64.deb
```

Показывает содержимое архива с путями, правами и размерами. Именно здесь проверяется, что файлы попали в предназначенные каталоги, а не, например, в `/usr/local`.

**После установки, по базе установленных пакетов** (`REQ-PKG-11`):

```bash
dpkg -L matching-engine
```

Ожидаемый вывод содержит, помимо каталогов:

```
/usr/bin/matching-engine-client
/usr/bin/matching-engine-server
/etc/matching-engine/config.json
/etc/matching-engine/matching-engine.env.example
/usr/share/matching-engine/database/001_init.sql
/usr/share/matching-engine/database/002_indexes.sql
/lib/systemd/system/matching-engine.service
```

**Метаданные:**

```bash
dpkg -s matching-engine                     # версия, зависимости, описание, сопровождающий
dpkg-deb --info matching-engine_1.0.0_amd64.deb
```

**Целостность установленного** — сверка контрольных сумм файлов пакета с тем, что лежит на диске:

```bash
sudo dpkg -V matching-engine
```

Пустой вывод означает, что ни один установленный файл не изменён. Изменённый `config.json` в выводе появиться не должен — файлы настроек из проверки исключены, и это ещё один способ убедиться, что пометка из раздела 3 действует.
