# Code review по требованиям ДЗ-3

Финальный этап проекта: разбор кода на соответствие всем 59 требованиям `task3.md`,
самостоятельная оценка найденных расхождений и правки по тем, что приняты. Порядок —
сначала разбор без внесения изменений в код, затем оценка, затем правки.

Разбор проведён двумя независимыми проходами по всему `src/`/`include/` — один по чек-листу
требований `task3.md` построчно, второй сфокусирован на управлении ресурсами и на семи
пунктах, которые задание выделяет особо как «нарушаемые незаметно». Оба прохода читали код
заново, без доверия статусам, ранее проставленным по ходу задач 00–13.

## 1. Архитектура

Проект состоит из четырёх слоёв, не пересекающих границы напрямую:

- **Разбор и вывод** — `CommandParser` (JSON → `Command`), `ReportPrinter` (единственный
  класс с `std::cout`, плюс `printUsage`/`printError` в stderr), `Logger` (singleton-обёртка
  над spdlog, весь лог — в stderr).
- **Домен** — `MatchingEngine`/`OrderBook`/`Order`/`Trade`. Не знает ни про JSON и `argv`
  (инвариант ещё ДЗ-2), ни про SQL и libpq (инвариант, добавленный ДЗ-3). Наружу отдаёт
  доменное DTO `ExecutionResult`/`OrderChange`, не зная, что с ним будет дальше.
- **Persistence** — `PersistenceService` (единственный класс, где создаётся `PgTransaction`;
  методы `save` для одной команды и `saveBatch` для пакета в режиме `--replay --batch`),
  три репозитория (`OrderRepository`/`TradeRepository`/`CommandRepository`, не хранят
  соединение полем), RAII-обёртка над libpq (`PgConnection`/`PgResult`/`PgTransaction`),
  `RecoveryService` (восстановление при старте), `SequenceGenerator`, `CommandCache`.
- **Оркестрация** — `Application` (`argv`, конфигурация, цепочка старта, обычный режим и
  `--replay`), `CommandProcessor` (идемпотентность + сопоставление + сохранение для одной
  команды).

## 2. Поток обработки одной команды ADD

`main()` создаёт `Application` и передаёт ей `argv`. `Application::run`:

1. разбирает аргументы (`--config`, `--replay`, `--batch` или позиционный JSON);
2. читает `DatabaseConfig` — host/port/dbname/user из JSON-файла, пароль только из
   `MATCHING_ENGINE_DB_PASSWORD`;
3. открывает единственное на весь процесс соединение `PgConnection`;
4. применяет схему БД идемпотентными `CREATE ... IF NOT EXISTS` из `database/*.sql`;
5. вызывает `recoverState` — поднимает активные заявки в книгу, восстанавливает
   `SequenceGenerator` по максимуму `sequence_number` **по всей таблице**, прогревает
   `CommandCache` из `processed_commands`.

Дальше — собственно ADD. `CommandParser::parse` превращает элемент JSON-массива `commands`
в `AddCommand` (или `MarketAddCommand`, если в JSON есть `order_type`); на этом этапе система
не знает ни про БД, ни про идемпотентность. `CommandProcessor::process`:

1. проверяет `command_id` — без него команда не выполняется (`ParseError`);
2. смотрит в `CommandCache::find` — если `command_id` уже встречался, возвращает старый
   `ExecutionResult`, не трогая ни книгу, ни БД;
3. иначе вызывает `MatchingEngine::process` → `processAdd`: заявка создаётся,
   `match`/`tryMatchBuy`/`tryMatchSell`/`executeTrade` сопоставляют её против противоположной
   стороны `OrderBook` (Price-Time Priority через `std::map<price, deque>` +
   `unordered_map<id, Order>`), и если заявка не исполнилась полностью — кладётся в книгу;
   результат — `ExecutionResult{trades, orderChanges}`, доменное DTO;
4. сохраняет результат одной транзакцией через `PersistenceService::save`: `PgTransaction`
   (RAII BEGIN/COMMIT/ROLLBACK), все `OrderChange` через `OrderRepository::save` (заявки
   раньше сделок — внешний ключ `trades → orders`), затем `Trade` через
   `TradeRepository::insert`, затем отметка команды через `CommandRepository::save`, коммит;
   при любой ошибке `PgTransaction` откатывается в своём деструкторе, исключение
   оборачивается в `PersistenceError`;
5. только после успешного `commit()` кладёт результат в `CommandCache::put` — если бы кеш
   обновлялся раньше сохранения, а транзакция затем не удалась, повтор команды после падения
   вернул бы результат, которого в БД никогда не было.

`PersistenceError` не перехватывается общим `catch(MatchingEngineError&)` в
`Application::processCommand` — пробрасывается явно и долетает до `Application::run`, где
процесс завершается с кодом 1 (fail-fast: книга в памяти уже разошлась с БД, продолжать
нельзя). Обычные доменные ошибки (`ParseError`, `OrderBookError` и т. д.), наоборот, гасятся
на границе одной команды, печатаются как `ERROR:` через `ReportPrinter` в stderr и не
прерывают обработку остальных команд пакета.

## 3. Разбор по всем 59 требованиям

Каждый вывод получен заново по коду, без доверия статусам `task3.md` на входе.

### DB — Схема и хранение (8/8 подтверждено)

Три таблицы `orders`/`trades`/`processed_commands` (`database/001_init.sql`), все требуемые
поля и ограничения на месте, `CHECK` на четыре статуса, схема применяется автоматически
(`applySchema`, `application.cpp`). Индексы — первичные ключи на `order_id`/`command_id` плюс
частичный `idx_orders_active_sequence` под выборку активных заявок (`database/002_indexes.sql`).
Находок нет.

### RAII — Обёртка над libpq (9/9 подтверждено)

`PgConnection`/`PgResult`/`PgTransaction` — три отдельных класса, копирование запрещено,
перемещение реализовано вручную (не `noexcept`, бросает при живой транзакции — намеренно, см.
задачу 06). Освобождение — через `unique_ptr` с собственными удалителями (`PQfinish`/`PQclear`
встречаются ровно по одному разу каждый, в теле удалителя). Владеющих сырых указателей вне
удалителей нет (`grep` по `new`/`delete`/`malloc`/`free` — пусто). Заголовки обёртки объявляют
только тег структуры (`struct pg_conn;`), не включают `libpq-fe.h` — типы драйвера не видны
транзитивно. `Application` не объявляет деструктор, соединение живёт в `std::optional` внутри
`run()`. Находок нет.

### ARCH — Разделение ответственности (6/6 подтверждено)

`grep` по SQL-литералам и по `pg_connection.hpp`/`libpq-fe.h` в `matching_engine.*`/
`order_book.*` — пусто. Все три репозитория реализуют требуемые операции. Обоснование
разделения — README.md, раздел «Архитектура», абзац «Принцип разделения ответственности».
Находок нет.

### REC — Восстановление состояния (5/5 подтверждено)

Порядок старта дословно соответствует требованию. `Order` восстанавливает `sequence_number`
как есть, не обращаясь к `SequenceGenerator`. `OrderBook::restore` вызывает только `addOrder`
— прослежен весь путь `RecoveryService::recoverState` → `CommandProcessor::restoreOrder` →
`MatchingEngine::restore` → `OrderBook::restore`, ни на одном шаге нет вызова
`match`/`matchMarket`/`tryMatchBuy*`/`tryMatchSell*`/`executeTrade`/`executeMarketTrade` —
сделка при восстановлении принципиально не может возникнуть. Подтверждено тестом
`CommandProcessorTest.RestoreOrderPutsCrossingOrdersIntoBookWithoutMatching`. Пять этапов
старта видны в логе (`Application::run` + `recovery_service.cpp`). Находок нет.

### IDEM — Идемпотентность (6/6 подтверждено)

Поток «кеш → matching → транзакция → `cache_.put`» выдержан дословно. `CommandCache::find`
предшествует любому обращению к БД. Прогрев при старте — `CommandRepository::loadAll` →
`warmCache`. Находок нет.

### TX — Транзакции и безопасность SQL (4/4 подтверждено)

Одна `PgTransaction` на команду (`PersistenceService::save`); `saveBatch` — документированный
размен для `--replay --batch`, штатный путь не тронут. `ROLLBACK` в деструкторе транзакции при
отсутствии `commit()`. Конкатенация в SQL — только для номеров плейсхолдеров и статических
фрагментов схемы (имена колонок, `ON CONFLICT`), проверено построчно во всех репозиториях и в
`include/sql_batch_insert.hpp`: ни одно значение не попадает в текст запроса. Находок нет.

### CFG — Конфигурация (2/2 подтверждено)

Параметры — из JSON-файла, пароль — только из переменной окружения. `config/database.json` не
отслеживается ни на одной ветке ни разу за всю историю (`git log --all -p -- config/database.json`

### TEST — Тестирование (7/7 подтверждено)

Контрольный прогон: **195/195**, включая все шесть сценариев ТЗ и семь интеграционных тестов

## 4. Находки

### Находка 1 — `MatchingEngine::trades_` растёт неограниченно

- **Требование.** Не отдельный REQ-ID; затрагивает дух REQ-PERF-01 (неограниченный рост
  ресурсов, созданных кодом проекта) и REQ-ARCH-02 (движок не должен держать журнал, для
  которого есть персистентный канал).
- **Файл и участок кода.** `include/matching_engine.hpp:24` (поле `std::vector<Trade> trades_`);
  заполняется в `src/matching_engine.cpp:91` (`processAdd`), `:235` (`processMarketAdd`),
  `:364` (`processModify`); читается через `trades()` (`:27`).
- **Описание проблемы.** Каждая совершённая сделка добавляется в `trades_` и никогда из него
  не удаляется на протяжении жизни процесса, хотя единственный потребитель этого поля —
  тесты `matching_engine_tests.cpp`. Рабочий путь приложения (`Application`,
  `PersistenceService`, `ReportPrinter`) читает сделки только через `ExecutionResult`,
  который `trades_` не задействует.
- **Почему это проблема.** На `--replay` (100 000+ команд, REQ-PERF-02) вектор копит все
  сделки за весь прогон в памяти без надобности — чистый расход без функции, частично
  нивелирующий эффект оптимизаций задачи 12 (пакетная запись экономит именно память и
  раунд-трипы, а этот вектор растёт параллельно им).
- **Рекомендуемое исправление.** Убрать поле и `trades()` целиком, если движок не должен
  нести историю дольше одной команды.

### Находка 2 — `std::cerr` в обход `ReportPrinter` при отсутствии аргументов

- **Требование.** Не отдельный REQ-ID; собственный архитектурный инвариант проекта
  («`ReportPrinter` — единственный класс с пользовательским выводом», README.md, раздел
  «Архитектура»).
- **Файл и участок кода.** `src/application.cpp`, ветка `parseError == kUsage` внутри
  `Application::run` — usage-сообщение печаталось напрямую в `std::cerr`, минуя
  `ReportPrinter`, тогда как для всех прочих ошибок разбора аргументов уже использовался
  `printer_.printError`.
- **Описание проблемы.** Второй, необъяснённый в документации канал пользовательского
  вывода — единственная брешь в инварианте на весь проект.
- **Почему это проблема.** Нарушает собственную границу слоёв без причины: остальные 100%
  пользовательского вывода идут через `ReportPrinter`, и будущий рефакторинг (например,
  перенаправление вывода в тестах) не заметил бы это единственное исключение.
- **Рекомендуемое исправление.** Добавить `ReportPrinter::printUsage()` (запись в `stderr`
  без префикса `ERROR:`, так как это не ошибка) и вызывать его вместо прямого `std::cerr <<`.
- **Статус:** принято и исправлено, см. §6.

### Находка 3 — сырой текст ошибки PostgreSQL уходит пользователю через `ERROR:`

- **Требование.** Конвенция, принятая проектом в задаче 03: сырой текст драйвера — только в
  отладочный лог, пользователю — человеческое сообщение (см. `describeConnectionFailure`/
  `describeSchemaFailure` в том же файле).
- **Файл и участок кода.** `src/application.cpp`, оба обработчика `catch(const
  PersistenceError& e)` (в `run()` — для обычного режима и для `--replay`) печатали
  `e.what()` целиком пользователю через `printer_.printError`. Источник сырого текста —
  `src/persistence_service.cpp` (`save`/`saveBatch`), где `PersistenceError` оборачивает
  необработанный `e.what()` от `DatabaseError`, несущего `PQerrorMessage`/
  `PQresultErrorMessage`.
- **Описание проблемы.** В отличие от симметричных обработчиков сбоя подключения и сбоя
  применения схемы в этом же файле, обработчики `PersistenceError` не прятали сырой текст в
  `debug`-лог, а показывали его пользователю целиком — вплоть до имени нарушенного
  ограничения, имени таблицы и фрагмента SQL.
- **Почему это проблема.** Несогласованность с уже принятым в проекте паттерном; раскрытие
  деталей реализации БД пользователю процесса — не критическая уязвимость в учебном проекте
  без внешних пользователей, но ровно тот тип регресса, который просачивается в реальный
  сервис, если код используется как основа.
- **Рекомендуемое исправление.** По аналогии с `describeConnectionFailure`/
  `describeSchemaFailure` завести `describePersistenceFailure()`, дать пользователю
  нейтральный текст без `e.what()`, а `e.what()` отправлять только через
  `Logger::instance().debug(...)`.
- **Статус:** принято и исправлено, см. §6.

## 5. Два зафиксированных, но не решённых напряжения (не новые находки)

- **Задача 09, критерий 7 (единый способ изоляции тестов).** В проекте два способа: откат
  транзакции для тестов репозиториев, очистка трёх таблиц для интеграционных тестов.
  Причина объективная — `PersistenceService` открывает и коммитит собственную транзакцию
  внутри вызова, внешний откат для сквозного сценария (через `Application`/`CommandProcessor`)
  недоступен по устройству кода. Единый способ здесь недостижим без ослабления одной из групп
  тестов. Зафиксировано как осознанное расхождение с буквой критерия конкретной внутренней
  задачи (не с REQ-ID `task3.md`), кандидат на уточнение формулировки человеком.
- **Задача 05, grep-критерий одной из внутренних задач.** Регистронезависимый поиск
  `PGconn|PGresult` ловил `PgConnection` как подстроку `pgconn`. Дефект формулировки
  конкретного критерия, не самого кода: по смыслу требование («SQL/тип драйвера не течёт за
  пределы обёртки», REQ-RAII-08) выполнено и подтверждено отдельно точным (с учётом регистра)
  поиском в этом же разборе (§3, RAII).

## 6. Самостоятельная оценка и внесённые правки

Из трёх находок:

### Правки (находки 2 и 3)

Изменены три файла: `include/report_printer.hpp`, `src/report_printer.cpp`,
`src/application.cpp`.

  прямого `std::cerr <<`.
- Добавлена `describePersistenceFailure()` — по образцу `describeConnectionFailure`/
  `describeSchemaFailure`: человеческое сообщение без `e.what()`. Оба обработчика
  `catch(const PersistenceError& e)` (обычный режим и `--replay`) теперь пишут
  `Logger::instance().error(describePersistenceFailure())` пользователю и
  `Logger::instance().debug(std::string("Persistence error: ") + e.what())` — сырой текст
  остался доступен для диагностики, но не в пользовательском выводе.

## 7. Финальная сверка трёх требований, не закрываемых отдельной задачей

- **REQ-PERF-05 (многопоточность).** `grep` по `<thread>`, `<future>`, `<mutex>`, `<atomic>`,
  `std::async`, `pthread` по всему `src/`/`include/`/`tests/` — ноль совпадений. Подтверждено
  дважды независимо (оба прохода разбора). **ГОТОВО.**
- **REQ-DOC-03 (ветка + Pull Request).** Работа велась в отдельной ветке `feature/data-base`
  (не в `main`) на всём протяжении ДЗ-3 — 15 коммитов, вся история персистентности. Ветка
  существует и корректна. Публикация ветки на удалённый репозиторий и создание Pull Request —
  завершающий шаг сдачи, выполняется человеком.
- **REQ-DOC-04 (Conventional Commits).** Все 15 коммитов ветки `feature/data-base`
  соответствуют формату `<type>(<scope>): <описание>` (`feat`/`test`/`perf`/`docs`, с
  областью и без). **ГОТОВО.**
