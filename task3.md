# ДЗ-3 — Persistent Matching Engine: требования

Требования ДЗ-3, разложенные по группам. У каждого требования свой идентификатор, чтобы на него можно было сослаться в коммите, тесте или обсуждении.

Статусы: `TODO` / `WIP` / `DONE`.

## DB — Схема и хранение

| ID | Требование | Статус |
|---|---|---|
| REQ-DB-01 | СУБД — PostgreSQL | ГОТОВО |
| REQ-DB-02 | Минимум три таблицы: `orders`, `trades`, `processed_commands` | ГОТОВО |
| REQ-DB-03 | `orders` хранит: `order_id`, `side`, `price`, `initial_quantity`, `remaining_quantity`, `status`, `sequence_number` | ГОТОВО |
| REQ-DB-04 | Статусы заявки: `OPEN`, `PARTIALLY_FILLED`, `FILLED`, `CANCELLED` | ГОТОВО |
| REQ-DB-05 | `trades` хранит: `trade_id`, `buy_order_id`, `sell_order_id`, `price`, `quantity` | ГОТОВО |
| REQ-DB-06 | `processed_commands` хранит: `command_id`, `command_type`, `status`, `result` | ГОТОВО |
| REQ-DB-07 | SQL-схема лежит в репозитории в `database/`; расчёт на ручное создание таблиц через psql запрещён | ГОТОВО |
| REQ-DB-08 | Определены индексы под запросы: поиск заявки по `order_id`, поиск команды по `command_id`, выборка активных заявок | ГОТОВО |

## RAII — Обёртка над libpq

| ID | Требование | Статус |
|---|---|---|
| REQ-RAII-01 | Работа с PostgreSQL только через C API `libpq` | ГОТОВО |
| REQ-RAII-02 | `libpqxx` не используется | ГОТОВО |
| REQ-RAII-03 | Собственная объектная обёртка: соединение, результат запроса, транзакция | ГОТОВО |
| REQ-RAII-04 | Класс соединения некопируемый, перемещаемый; деструктор закрывает соединение, ручной вызов `PQfinish` не требуется | ГОТОВО |
| REQ-RAII-05 | Класс результата освобождает `PQclear` автоматически | ГОТОВО |
| REQ-RAII-06 | Класс транзакции: выход из области видимости без `commit()` выполняет rollback | ГОТОВО |
| REQ-RAII-07 | Владеющие сырые указатели в коде приложения отсутствуют | ГОТОВО |
| REQ-RAII-08 | `PGconn*` и `PGresult*` существуют только внутри низкоуровневой обёртки и не распространяются по приложению | ГОТОВО |
| REQ-RAII-09 | Штатное завершение освобождает соединение, результаты запросов и кеш без ручных вызовов в деструкторе `Application` | ГОТОВО |

| ID | Требование | Статус |
|---|---|---|
| REQ-ARCH-01 | SQL не находится внутри `MatchingEngine`; работа с БД вынесена отдельно | ГОТОВО |
| REQ-ARCH-02 | `MatchingEngine` не знает о драйвере PostgreSQL, тексте SQL и схеме БД | ГОТОВО |
| REQ-ARCH-03 | `OrderRepository`: вставка, обновление и отмена заявки, загрузка активных заявок | ГОТОВО |
| REQ-ARCH-04 | `TradeRepository`: вставка сделки, загрузка сделок | ГОТОВО |
| REQ-ARCH-05 | `CommandRepository`: сохранение, поиск и загрузка обработанных команд | ГОТОВО |
| REQ-ARCH-06 | Разделение ответственности обосновано в README | TODO |

## REC — Восстановление состояния

| ID | Требование | Статус |
|---|---|---|
| REQ-REC-01 | После перезапуска состояние биржи не теряется, Order Book восстанавливается | ГОТОВО |
| REQ-REC-02 | Порядок старта: подключение к БД → чтение активных заявок → восстановление Order Book → восстановление `sequence_number` → прогрев кеша → обработка новых команд | ГОТОВО |
| REQ-REC-03 | Каждая заявка хранит монотонно возрастающий `sequence_number`; Price-Time Priority сохраняется между перезапусками | ГОТОВО |
| REQ-REC-04 | Восстановленные заявки не проходят повторное сопоставление — предусмотрен отдельный механизм восстановления | ГОТОВО |
| REQ-REC-05 | В логах видны этапы старта: подключение к БД, восстановление книги, число восстановленных заявок, прогрев кеша, готовность движка | ГОТОВО |

## IDEM — Идемпотентность

| ID | Требование | Статус |
|---|---|---|
| REQ-IDEM-01 | Каждая изменяющая состояние команда содержит уникальный `command_id` | ГОТОВО |
| REQ-IDEM-02 | Повторная команда с известным `command_id` не добавляет заявку, не совершает сделок, не меняет Order Book и не создаёт записей в `trades` | ГОТОВО |
| REQ-IDEM-03 | На повторную команду возвращается результат предыдущего выполнения | ГОТОВО |
| REQ-IDEM-04 | In-memory кеш `command_id` → результат выполнения | ГОТОВО |
| REQ-IDEM-05 | При старте кеш прогревается из `processed_commands`; проверка идёт прежде всего в памяти | ГОТОВО |
| REQ-IDEM-06 | Поток обработки: команда → кеш (найдено — вернуть прошлый результат) → matching → транзакция БД → обновление кеша | ГОТОВО |

## TX — Транзакции и безопасность SQL

| ID | Требование | Статус |
|---|---|---|
| REQ-TX-01 | Все изменения одной команды сохраняются атомарно: обновление существующих заявок, новая заявка, все сделки, запись обработанной команды | ГОТОВО |
| REQ-TX-02 | Одна изменяющая команда — одна логическая транзакция БД: либо всё, либо ничего | ГОТОВО |
| REQ-TX-03 | При ошибке выполняется `ROLLBACK` | ГОТОВО |
| REQ-TX-04 | SQL не собирается конкатенацией строк; используются параметризованные запросы | ЧАСТИЧНО (задачи 01, 06) |
