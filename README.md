# Matching Engine

Упрощённый биржевой движок сопоставления заявок (Matching Engine). Программа принимает заявки на покупку и продажу финансового инструмента, хранит активные заявки в книге заявок (Order Book) и автоматически совершает сделки, когда цена покупателя пересекается с ценой продавца.

## Принцип работы Limit Order Book

**Limit Order** — заявка с явно указанной ценой. Покупатель указывает максимальную цену, которую готов заплатить; продавец — минимальную цену, за которую готов продать.

**Книга заявок (Order Book)** хранит все активные лимитные заявки, упорядоченные по цене и времени поступления. Она состоит из двух сторон:

- **BUY (Bid)** — заявки на покупку, отсортированные по убыванию цены (лучшая — самая высокая цена)
- **SELL (Ask)** — заявки на продажу, отсортированные по возрастанию цены (лучшая — самая низкая цена)

**Сделка** совершается, когда цена лучшей SELL-заявки не превышает цену лучшей BUY-заявки, то есть когда спред пересекается:

```
BUY price >= SELL price → сделка возможна
```

**Цена сделки** определяется ценой заявки, которая уже находилась в книге на момент поступления встречной заявки.

## Price-Time Priority

Алгоритм сопоставления реализует приоритет **Price-Time**:

**1. Price Priority** — в первую очередь исполняются заявки с лучшей ценой:

- Для BUY: чем выше цена, тем выше приоритет
- Для SELL: чем ниже цена, тем выше приоритет

```
SELL в книге:   99 → 100 → 101   (приоритет слева направо)
BUY  в книге:  101 → 100 →  99   (приоритет слева направо)
```

**2. Time Priority** — при одинаковой цене первой исполняется заявка, поступившая раньше (FIFO):

```
Три BUY-заявки по цене 100, поступившие в порядке #10 → #20 → #30:
Приоритет: #10 > #20 > #30
```

Одна входящая заявка может породить несколько сделок подряд — движок продолжает сопоставление, пока заявка не исполнена полностью или в книге не осталось подходящих встречных заявок.

## Архитектура

```
main()
  │
  └─► Application
        │
        ├─► CommandParser        парсинг JSON → объекты Command
        │
        ├─► CommandProcessor     идемпотентность + сопоставление + сохранение для одной команды
        │       │
        │       ├─► CommandCache       command_id → ExecutionResult (in-memory)
        │       │
        │       ├─► MatchingEngine     бизнес-логика (не знает о JSON, stdout и БД)
        │       │       │
        │       │       └─► OrderBook  хранение активных заявок
        │       │
        │       └─► PersistenceService сохранение заявок, сделок и отметки команды одной транзакцией
        │               │
        │               ├─► OrderRepository / TradeRepository / CommandRepository   SQL трёх таблиц
        │               │
        │               └─► PgConnection / PgResult / PgTransaction   RAII-обёртка над libpq
        │
        ├─► RecoveryService     восстановление книги, счётчика и кеша при старте
        │
        ├─► AppConfig           конфигурация сервера и БД (файл + переменная окружения)
        │
        ├─► ReportPrinter       вывод в stdout (только консольный режим)
        │
        └─► Logger              Singleton-обёртка над spdlog
```

Диаграмма выше описывает консольный режим (`matching_engine`). Серверный режим (`matching-engine-server`) надстраивает сетевой слой поверх того же движка, не проникая внутрь него — `CommandProcessor` и всё, что ниже, используются без изменений:

```
matching-engine-server
  │
  ├─► SignalHandler        сигнальный поток: sigwait(SIGTERM, SIGINT, SIGUSR1), передаёт остановку через post
  │
  └─► Server                владеет acceptor, реестром сессий, запуском и остановкой
        │
        └─► Session (на каждое соединение)
                │
                ├─► MessageCodec        кодирование/декодирование кадра (заголовок + JSON)
                │
                ├─► RequestRouter       разбор запроса, маршрутизация PING/HEALTH/PRINT/ADD/CANCEL/MODIFY
                │       │
                │       └─► CommandProcessor …   тот же путь, что и в консольном режиме
                │
                └─► ResponseSerializer  сборка JSON-ответа клиенту

matching-engine-client
  │
  └─► Client                подключение, отправка и приём кадров (тот же MessageCodec)
```

`MatchingEngine` и `OrderBook` не знают о `Server`, `Session`, `MessageCodec`, Boost.Asio и формате кадра — граница между движком и сетью проведена так же строго, как граница между движком и БД.

### Описание классов

| Класс | Ответственность |
|---|---|
| `Application` | Читает `argv`, оркестрирует парсинг, выполнение команд, восстановление и вывод результатов |
| `CommandParser` | Валидирует JSON, проверяет поля и типы, создаёт объекты `Command` |
| `Command` / `AddCommand` / `CancelCommand` / `PrintCommand` | Иерархия команд — передают данные от парсера к движку |
| `MatchingEngine` | Принимает команды, запускает алгоритм сопоставления, хранит историю сделок |
| `OrderBook` | Хранит активные заявки с поддержкой Price-Time Priority |
| `Order` | Одна биржевая заявка; валидирует себя при создании |
| `Trade` | Результат сделки: `buyOrderId`, `sellOrderId`, `price`, `quantity` |
| `ExecutionResult` / `OrderChange` | DTO, которым движок сообщает наружу об изменениях (заявки, сделки), не зная о БД |
| `CommandProcessor` | Связывает кеш идемпотентности, движок и сохранение в БД для одной изменяющей команды |
| `CommandCache` | In-memory отображение `command_id → ExecutionResult` для идемпотентности повторов |
| `PersistenceService` | Единственный класс, где создаётся `PgTransaction`; сохраняет заявки, затем сделки, затем запись о команде — одной транзакцией (штатно) или пакетом (`--batch`) |
| `OrderRepository` / `TradeRepository` / `CommandRepository` | SQL для таблиц `orders`, `trades`, `processed_commands`; соединение получают параметром, не хранят |
| `PgConnection` / `PgResult` / `PgTransaction` | RAII-обёртка над libpq |
| `AppConfig` / `ServerConfig` / `DatabaseConfig` / `loadConfig` | Единый формат конфигурации: секции `server` и `database` |
| `RecoveryService` (`recoverState`) | Восстановление книги, счётчика номеров заявок и кеша идемпотентности при старте |
| `SequenceGenerator` | Монотонный счётчик номеров заявок |
| `ReportPrinter` | Выводит сделки, состояние книги и ошибки |
| `Logger` | Singleton Мейерса над spdlog; остальные компоненты не включают `spdlog.h` |
| `Server` | Владеет `acceptor`, принимает подключения, ведёт реестр сессий, останавливает приём и дренирует соединения при остановке |
| `Session` | Одно TCP-соединение: сокет, чтение заголовка и тела кадра, разбор запроса, очередь записи ответов, время жизни через `shared_ptr`/`shared_from_this` |
| `MessageCodec` | Кодирование/декодирование кадра (4 байта длины в сетевом порядке + JSON); вся работа с `htonl`/`ntohl`/`memcpy` сосредоточена здесь |
| `RequestRouter` | Разбор JSON запроса и маршрутизация по типу команды к `CommandProcessor` либо к служебным `PING`/`HEALTH`/`PRINT` |
| `ResponseSerializer` | Сборка JSON-ответа клиенту (`status`, `trades`, `error`) — формат ответа, отдельный от формата хранения в БД |
| `SignalHandler` | Отдельный класс для сигналов: блокирует `SIGTERM`/`SIGINT`/`SIGUSR1`, ведёт сигнальный поток на `sigwait`, передаёт запрос остановки владельцу сервера |
| `Client` | Подключение к серверу, отправка и приём кадров тем же `MessageCodec`; используется и `matching-engine-client`, и сетевыми тестами |

**Принцип разделения ответственности:** `MatchingEngine` не парсит JSON, не читает `argc`/`argv`, не пишет в консоль и не обращается к spdlog напрямую. В консольном режиме (`matching_engine`) `ReportPrinter` — единственный класс, пишущий в `std::cout`; в серверном режиме `std::cout` не используется вовсе, а результат уходит клиенту по сети (подробнее — в разделе [Threading Model](#threading-model) и в описании [TCP API](#tcp-api)); клиентская программа `matching-engine-client`, в свою очередь, печатает в `std::cout` полученные от сервера ответы. Этот же принцип действует и в другую сторону: `MatchingEngine` и `OrderBook` точно так же не видят SQL и не включают заголовки libpq — весь доступ к базе данных сосредоточен в `PersistenceService` и репозиториях, а движку наружу отдаются только доменные DTO (`ExecutionResult`/`OrderChange`). Сетевой слой соблюдает ту же границу: `MatchingEngine` и `OrderBook` не знают ни о сокетах, ни о Boost.Asio, ни о формате кадра.

## Структуры данных

### Хранилище заявок в OrderBook

Для хранения заявок выбрана двухуровневая структура:

```cpp
std::map<int, std::deque<std::shared_ptr<Order>>> buyLevels_;
std::map<int, std::deque<std::shared_ptr<Order>>> sellLevels_;
std::unordered_map<int, std::shared_ptr<Order>>   ordersById_;
```

**Почему `std::map<price, deque>`?**

- `std::map` хранит ключи (цены) в отсортированном порядке и не требует `std::sort` после каждой вставки. Вставка и удаление — O(log N).
- Для BUY лучшая цена — максимальная: итерируемся через `rbegin()`.
- Для SELL лучшая цена — минимальная: итерируемся через `begin()`.
- Пустые ценовые уровни удаляются из `map` автоматически.

**Почему `std::deque` внутри уровня цены?**

- Реализует FIFO: `push_back` при добавлении, `front` для чтения лучшей заявки.
- Поддерживает Time Priority без дополнительной сортировки.

**Почему `std::unordered_map<id, Order>`?**

- Поиск и удаление заявки по `id` за O(1) — необходимо для команды `CANCEL` и проверки дубликатов.

**Итоговые сложности:**

| Операция | Сложность |
|---|---|
| Добавить заявку | O(log N) |
| Удалить заявку по id | O(log N) |
| Найти заявку по id | O(1) |
| Получить лучшую BUY / SELL | O(1) |
| Итерация для PRINT | O(N) |

## Формат JSON-команд

Программа принимает JSON-объект с массивом `"commands"` через аргумент командной строки.

**Идентификатор заявки: `id` и `order_id`.** Ниже, в примерах пакетного режима, поле называется `id` — так было в предыдущих версиях проекта, и вся история тестов и документации этого режима держится на этом имени. Сетевой API (раздел [TCP API](#tcp-api)) передаёт одну команду на кадр и называет то же поле `order_id`; разбор команд принимает оба имени как синонимы одного и того же идентификатора — какое из них прислали, такое и используется. Ниже везде, где это не оговорено отдельно, читайте `id` и `order_id` как взаимозаменяемые названия одного поля.

### ADD — добавить заявку

```json
{
    "type": "ADD",
    "id": 1,
    "side": "BUY",
    "price": 100,
    "quantity": 10,
    "command_id": "add-example-1"
}
```

| Поле | Тип | Описание |
|---|---|---|
| `type` | string | `"ADD"` |
| `id` | int > 0 | Уникальный идентификатор заявки |
| `side` | string | `"BUY"` или `"SELL"` |
| `price` | int > 0 | Цена заявки |
| `quantity` | int > 0 | Количество |
| `command_id` | string | Уникальный идентификатор команды; обязателен для изменяющих команд (ADD, CANCEL, MODIFY) и обеспечивает идемпотентность — повтор с тем же `command_id` не меняет книгу, не создаёт новых сделок и возвращает прошлый результат. `PRINT` этого поля не требует |

### CANCEL — отменить заявку

```json
{
    "type": "CANCEL",
    "id": 1,
    "command_id": "cancel-example-1"
}
```

### PRINT — вывести книгу заявок

```json
{
    "type": "PRINT"
}
```

### Полный пример входных данных

```json
{
    "commands": [
        { "type": "ADD",    "id": 1, "side": "BUY",  "price": 100, "quantity": 10, "command_id": "full-example-add-1" },
        { "type": "ADD",    "id": 2, "side": "SELL",  "price": 105, "quantity": 5, "command_id": "full-example-add-2" },
        { "type": "ADD",    "id": 3, "side": "SELL",  "price": 99,  "quantity": 7, "command_id": "full-example-add-3" },
        { "type": "PRINT" },
        { "type": "CANCEL", "id": 2, "command_id": "full-example-cancel-1" },
        { "type": "PRINT" }
    ]
}
```

## Сборка

**Требования:** CMake ≥ 3.20, компилятор с поддержкой C++17 (GCC 13+ / Clang 16+), интернет для FetchContent, системные библиотеки Boost (заголовки; сборка проверена с 1.83, минимальной версии не требует) и `libpq` (клиентская библиотека PostgreSQL). Обе ставятся из пакетов дистрибутива (например, `libboost-dev`, `libpq-dev`) — через FetchContent не подтягиваются.

Зависимости (`nlohmann/json`, `GoogleTest`, `spdlog`) загружаются автоматически при первой сборке. Сетевой слой использует Boost.Asio в header-only варианте: линковка с библиотекой Boost не требуется, только заголовки и `-pthread`.

```bash
git clone <repo-url>
cd matching_engine

cmake -B build
cmake --build build
```

Тип сборки по умолчанию — `Release` (`-O3 -DNDEBUG`); он задан в `CMakeLists.txt` и действует, когда тип не указан явно. Значение из командной строки его перекрывает: `cmake -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo`. Конфигурация с ThreadSanitizer (`-DENABLE_TSAN=ON`, раздел [Threading Model](#threading-model)) всегда собирается как `RelWithDebInfo` — санитайзеру нужны отладочная информация и фрейм-поинтеры.

После сборки в директории `build` появятся четыре бинарника:
- `matching_engine` — пакетная обработка команд и режим `--replay` (прежний консольный режим)
- `matching-engine-server` — TCP-сервер
- `matching-engine-client` — консольный клиент к серверу
- `matching_engine_tests` — тестовый бинарь

## Запуск

Проект собирает три исполняемых файла с разным назначением:

| Бинарник | Назначение |
|---|---|
| `matching_engine` | пакетная обработка одного JSON-пакета команд или файла нагрузки (`--replay`); обрабатывает переданные команды и завершается |
| `matching-engine-server` | TCP-сервер: слушает порт и обслуживает подключения клиентов, пока не получит сигнал остановки |
| `matching-engine-client` | консольный клиент к серверу: подключается по TCP, отправляет команды, печатает ответы |

Разница по существу: `matching_engine` — программа, отработавшая и завершившаяся (пакетный режим ДЗ-2/ДЗ-3); `matching-engine-server` и `matching-engine-client` — постоянно работающая служба и клиент к ней (сетевой режим этой работы, разделы [Network Protocol](#network-protocol) и [TCP API](#tcp-api)). Оба режима работают с одной и той же базой и одним и тем же движком сопоставления.

Для запуска в любом из режимов нужен доступный сервер PostgreSQL: при старте приложение подключается к нему и само создаёт схему (таблицы и индексы) из файлов каталога со схемой, вручную создавать таблицы через `psql` не нужно. Параметры подключения (хост, порт, имя базы, пользователь) и путь к каталогу со схемой берутся из секции `database` файла `config/config.json` (образец без пароля — `config/config.example.json`), путь к самому файлу конфигурации переопределяется ключом `--config`. Поле `database.schema_dir` обязательно — без него `loadConfig` завершается ошибкой; для запуска из каталога сборки указывается путь к каталогу `database/` в корне репозитория. Пароль передаётся только через переменную окружения `MATCHING_ENGINE_DB_PASSWORD` и в файлы конфигурации не попадает.

### Пакетный режим (`matching_engine`)

```bash
./build/matching_engine '<json>'
```

JSON передаётся одним аргументом командной строки. Рекомендуется обернуть в одинарные кавычки, чтобы экранировать от shell.

**Пример:**

```bash
./build/matching_engine '{
    "commands": [
        { "type": "ADD",  "id": 1, "side": "BUY",  "price": 100, "quantity": 10, "command_id": "run-example-add-1" },
        { "type": "ADD",  "id": 2, "side": "SELL",  "price": 99,  "quantity": 7, "command_id": "run-example-add-2" },
        { "type": "PRINT" }
    ]
}'
```

### Режим воспроизведения нагрузки (`--replay`)

Вместо одного JSON-пакета можно прогнать файл в формате JSON Lines — по одной команде на строку, тот же формат, что принимает обычный режим (`command_id` обязателен для изменяющих команд). Файл читается построчно, не загружается в память целиком:

```bash
./build/matching_engine --replay workload.jsonl
```

Некорректная строка не прерывает прогон — печатается `ERROR:` и обработка продолжается со следующей строки. После прогона выводится сводка (`REPLAY SUMMARY`): сколько команд обработано (записано в БД), сколько сделок совершено, сколько строк оказались повторами или ошибками, сколько заняло времени.

Генератор тестового файла нагрузки — `scripts/generate_workload.py`:

```bash
python3 scripts/generate_workload.py --count 100000 --output workload.jsonl
```

Выдаёт детерминированную (по умолчанию зерно 42) смесь заявок на обеих сторонах книги, часть — с пересечением цен ради сделок, часть — глубоко в книге как цели для отмен; идентификаторы заявок и команд уникальны в пределах файла.

С ключом `--batch` (только вместе с `--replay`) запись в БД идёт пакетами по несколько сотен команд одной транзакцией вместо одной транзакции на команду — способ сравнить пропускную способность обеих схем записи. Это осознанный размен атомарности ради измерений, а не альтернативный штатный режим: подробности и числа — в разделе [Оптимизации](#оптимизации-подготовленные-запросы-и-пакетная-запись).

```bash
./build/matching_engine --replay workload.jsonl --batch
```

### Сервер и клиент (`matching-engine-server`, `matching-engine-client`)

```bash

```

Сервер использует ту же конфигурацию, что и пакетный режим, — секция `server` дополнительно задаёт адрес, порт и максимальный размер сообщения. ## Network Protocol

`matching-engine-server` не полагается на границы TCP-чтения: одно сообщение клиента может прийти несколькими частями, а несколько сообщений — одним пакетом. Границу сообщения задаёт собственный формат кадра.

```
 0       1       2       3       4                        4 + N
 +-------+-------+-------+-------+------------------------+
 |          размер N (uint32)    |   полезная нагрузка    |
 |        сетевой порядок        |    ровно N байт JSON   |
 +-------+-------+-------+-------+------------------------+
```

| Свойство | Значение |
|---|---|
| Заголовок | 4 байта, `uint32_t` — длина полезной нагрузки |
| Порядок байт | сетевой (старший байт первым, `htonl`/`ntohl`) |
| Полезная нагрузка | ровно N байт: один JSON-объект в UTF-8 |
| Максимальный размер | `server.max_message_size` из конфигурации, по умолчанию 1 МБ |

Длина в заголовке — это длина только полезной нагрузки, сами четыре байта заголовка в неё не входят; кадр целиком занимает `4 + N` байт. Кадр с нулевой длиной полезной нагрузки допустим на уровне протокола: следующий кадр начинается сразу за заголовком, а пустая строка отклоняется уже на уровне разбора JSON как ошибка запроса.

Заявленный клиентом размер проверяется сразу после разбора заголовка и до выделения памяти под тело: заголовок, объявляющий 2 ГБ, не приводит к попытке выделить 2 ГБ. Если заявленный размер запроса больше `server.max_message_size`, сервер отвечает ошибкой `MESSAGE_TOO_LARGE` и закрывает соединение — читать дальше по такому потоку небезопасно. Если, наоборот, корректный запрос порождает слишком большой ответ (например, `PRINT` на очень большой книге), сервер отвечает `RESPONSE_TOO_LARGE` и соединение остаётся открытым — это ошибка размера ответа, а не протокола.

Вся работа с двоичным представлением (`htonl`, `ntohl`, побайтовая сборка кадра) сосредоточена в одном компоненте кодека и не встречается ни в сессии, ни в сервере, ни в клиенте; сервер и клиент используют один и тот же кодек, поэтому расхождение формата между ними исключено.

## TCP API

Полезная нагрузка одного кадра — ровно один JSON-объект с одной командой; один кадр — одна команда — один ответ.

| Команда | Обязательные поля | Пример запроса |
|---|---|---|
| `ADD` (лимитная) | `order_id`, `side`, `price`, `quantity`, `command_id` | `{"type":"ADD","order_id":1,"side":"BUY","price":100,"quantity":10,"command_id":"cmd-1001"}` |
| `ADD` (рыночная) | `order_id`, `side`, `quantity`, `order_type` со значением `MARKET`, `command_id` | `{"type":"ADD","order_type":"MARKET","order_id":7,"side":"SELL","quantity":5,"command_id":"cmd-1007"}` |
| `CANCEL` | `order_id`, `command_id` | `{"type":"CANCEL","order_id":1,"command_id":"cmd-55"}` |
| `MODIFY` | `order_id`, `price`, `quantity`, `command_id` | `{"type":"MODIFY","order_id":1,"price":101,"quantity":8,"command_id":"cmd-72"}` |
| `PRINT` | — | `{"type":"PRINT"}` |
| `PING` | — | `{"type":"PING"}` |
| `HEALTH` | — | `{"type":"HEALTH"}` |

Идентификатор заявки передаётся полем `order_id`; имя `id`, унаследованное от пакетного режима, принимается как синоним. `ADD`, `CANCEL` и `MODIFY` изменяют состояние и требуют `command_id` — на нём держится идемпотентность. `PRINT`, `PING` и `HEALTH` состояние не меняют, в базу не пишутся и `command_id` не требуют.

Ответ на успешную изменяющую команду:

```json
{
  "command_id": "cmd-1002",
  "status": "OK",
  "order_id": 2,
  "trades": [
    { "buy_order_id": 1, "sell_order_id": 2, "price": 100, "quantity": 7 }
  ]
}
```

`trades` присутствует всегда, даже пустым; `command_id` возвращается эхом. `PING` отвечает буквально `{"status":"OK","result":"PONG"}`, ничего не сохраняя и не изменяя. `HEALTH` отвечает `{"status":"OK","database":"CONNECTED","engine":"READY"}` (при недоступной базе — `"database":"DOWN"`), тоже ничего не меняя. `PRINT` возвращает снимок книги в порядке приоритета исполнения:

```json
{
  "status": "OK",
  "result": {
    "buy":  [ { "order_id": 1, "price": 100, "quantity": 3 } ],
    "sell": [ { "order_id": 5, "price": 101, "quantity": 10 } ]
  }
}
```

Ответ на ошибку:

```json
{
  "command_id": "cmd-55",
  "status": "ERROR",
  "error": "ORDER_NOT_FOUND",
  "message": "Order 999999 does not exist"
}
```

`error` — код для программы, `message` — описание для человека, оба на верхнем уровне объекта. Коды: `INVALID_REQUEST`, `INVALID_ORDER`, `DUPLICATE_ORDER`, `ORDER_NOT_FOUND`, `MESSAGE_TOO_LARGE`, `RESPONSE_TOO_LARGE`, `INTERNAL_ERROR`. Ошибка пользователя (битый JSON, отсутствующее поле, неизвестная команда, несуществующая заявка) не разрывает соединение и не роняет сервер — сессия продолжает читать из того же сокета, а остальные подключённые клиенты не затрагиваются. Повторная команда с тем же `command_id` возвращает в точности тот же ответ, что и первое выполнение, — включая список сделок, а не пустой результат.

## Threading Model

Сервер работает как минимум в двух потоках.

**Какие потоки есть и что им доступно.** Главный поток одновременно является сетевым: он выполняет `io_context.run()` и владеет всем изменяемым состоянием — `OrderBook`, `MatchingEngine`, `CommandProcessor` с кешем идемпотентности, соединением с PostgreSQL, `Server`, `acceptor`, всеми сессиями и их сокетами. Второй, сигнальный поток блокирует и ждёт `SIGTERM`/`SIGINT`/`SIGUSR1` через `sigwait` — своего изменяемого состояния он не имеет, кроме локальной переменной с номером полученного сигнала.

**Что разделяется между потоками.** По факту — ничего из перечисленного выше: сигнальный поток не читает и не пишет книгу заявок, сессии, соединение с базой. Единственная точка соприкосновения — `boost::asio::post(io_context, …)`, которым сигнальный поток передаёт в цикл событий одну задачу «начать остановку»; `post` потокобезопасен по контракту Boost.Asio.

**Как происходит остановка.** Сигнальный поток, получив `SIGTERM`/`SIGINT`, ничего не делает с сервером сам — он лишь передаёт запрос остановки через `post`. Дальше всё выполняется в сетевом потоке: закрывается `acceptor`, обходится реестр живых сессий, каждой сообщается, что нужно закрыться, а когда операций не остаётся — `io_context.run()` возвращается сама, без принудительного `stop()`. Подробная последовательность — в разделе [Graceful Shutdown](#graceful-shutdown).

**Где применяются `mutex` и `atomic`.** Нигде — в проекте нет ни одного `std::mutex` и ни одной атомарной переменной в схеме остановки. Мьютекс защищал бы данные, разделяемые между потоками, а таких данных здесь нет: изменяемое состояние движка целиком принадлежит одному потоку. Даже различение «пришёл сигнал остановки или пробуждение перед завершением» сделано не флагом-переменной, которую нужно было бы защищать, а номером сигнала, который вернул `sigwait`, — это локальная переменная одного потока, а не разделяемое состояние.

**Почему в архитектуре нет состояний гонки.** Единственный владелец `io_context` — сетевой поток; обработчики в нём не вытесняют друг друга, поэтому обработка одной команды (разбор, сопоставление, транзакция, постановка ответа в очередь) выполняется от начала до конца, не будучи прервана обработчиком остановки. Сигнальный поток не имеет доступа ни к чему, кроме `post`, поэтому у него физически нет объекта, который он мог бы разделить с сетевым потоком без синхронизации. Время жизни каждой сессии управляется `std::shared_ptr`/`std::enable_shared_from_this`, поэтому сессия не может быть разрушена, пока для неё есть незавершённая асинхронная операция. Отсутствие гонок в этой модели — не результат синхронизации данных, а следствие того, что разделяемых изменяемых данных между потоками попросту нет; там, где это утверждение проверяемо (передача события остановки, закрытие сессий, работа нескольких клиентов одновременно), оно подтверждено прогоном под ThreadSanitizer:

```bash
cmake -B build-tsan -DENABLE_TSAN=ON
cmake --build build-tsan -j$(nproc)
ctest --test-dir build-tsan
```

## Graceful Shutdown

После `SIGTERM` или `SIGINT` сервер останавливается в таком порядке:

1. сигнальный поток замечает сигнал на `sigwait` и передаёт запрос остановки в `io_context` через `post`;
2. `acceptor` закрывается — новые подключения больше не принимаются;
3. запускается контроль предельного времени остановки;
4. каждой живой сессии сообщается, что нужно закрыться: сессия без ожидающих в очереди ответов закрывает сокет сразу, а сессия с недописанным ответом — после того как допишет его до конца;
5. когда незавершённых операций не остаётся, `io_context.run()` возвращается сама;
6. сигнальному потоку посылается внутренний сигнал пробуждения, поток присоединяется;
7. `Server`, затем `io_context`, затем движок и соединение с PostgreSQL освобождаются деструкторами;
8. процесс завершается с кодом `0`.

Команда, начатая до прихода сигнала, всегда доводится до конца вместе со своей транзакцией — обработчик остановки не может выполниться посреди обработчика команды, потому что оба исполняются одним потоком без вытеснения. Если отведённое на остановку время истекает раньше, чем сессии успевают закрыться сами, сервер завершает цикл событий принудительно, но так же корректно — деструкторы отрабатывают, ресурсы освобождаются, только код возврата в этом случае ненулевой.

## systemd

Пакет устанавливает unit-файл `matching-engine.service`. Управление службой — обычными командами `systemctl`.

```bash
sudo systemctl daemon-reload                 # перечитать unit-файл после установки/изменения
sudo systemctl start matching-engine         # запустить службу
systemctl status matching-engine             # ожидается: Active: active (running)
sudo systemctl restart matching-engine       # SIGTERM старому процессу, ожидание, запуск нового
sudo systemctl stop matching-engine          # SIGTERM и graceful shutdown
journalctl -u matching-engine -f             # следить за журналом службы
```

`systemctl restart` посылает старому процессу `SIGTERM`, дожидается его корректного завершения и запускает новый — тот проходит обычный порядок старта и восстанавливает книгу заявок из PostgreSQL. Политика `Restart=on-failure` перезапускает службу только при ненулевом коде возврата; после явного `systemctl stop` служба остаётся остановленной. В журнале видны этапы работы: старт, подключение к базе, число восстановленных заявок, прогрев кеша, начало прослушивания порта, подключения клиентов, получение сигнала, остановка.

## Persistence

Каждая изменяющая команда (`ADD`, `CANCEL`, `MODIFY`) сохраняется в PostgreSQL атомарно: изменения затронутых заявок, совершённые сделки и отметка о том, что команда выполнена, пишутся одной транзакцией через `PersistenceService`. `PRINT` в БД не пишет вовсе — эта команда ничего не меняет в книге, ей нечего сохранять.

Движок (`MatchingEngine`/`OrderBook`) о существовании БД не знает: он возвращает наружу доменное DTO `ExecutionResult` (список изменённых заявок и совершённых сделок), а всё, что связано с SQL и libpq, сосредоточено в `PersistenceService` и репозиториях. Это то же разделение ответственности, которое в проекте уже действует между движком и `ReportPrinter`/JSON — сохранение состояния добавляет ещё одну границу того же рода, а не меняет существующие.

Подробности — в отдельных разделах: структура таблиц в [Database schema](#database-schema), гарантии одной транзакции в [Transactions](#transactions) и [Crash consistency](#crash-consistency), защита от повторной обработки в [Idempotency](#idempotency) и [Cache](#cache), восстановление состояния при старте в [Recovery](#recovery).

## Database schema

Схема состоит из трёх таблиц.

**`orders`** — книга заявок как она должна выглядеть в базе. `price` допускает `NULL`, потому что у рыночной заявки цены нет. `status` ограничен `CHECK`-условием на четыре значения (`OPEN`, `PARTIALLY_FILLED`, `FILLED`, `CANCELLED`) — заявка не может оказаться в состоянии, которого не существует в доменной модели. `sequence_number` уникален и монотонно возрастает; это не техническое поле, а то, что задаёт порядок восстановления книги и Price-Time Priority после рестарта (см. [Recovery](#recovery)).

**`trades`** — журнал совершённых сделок. `trade_id` не придумывается приложением, а выдаётся самой базой (`BIGSERIAL`) — это упрощает запись и снимает риск коллизии идентификаторов между процессами. `buy_order_id`/`sell_order_id` — внешние ключи на `orders(order_id)`, поэтому заявки обязаны быть записаны раньше сделок в той же транзакции: иначе внешний ключ отверг бы вставку сделки, ссылающейся на ещё не существующую в базе заявку.

**`processed_commands`** — журнал идемпотентности. `result` хранится как `JSONB` с сериализованным `ExecutionResult` (сделки и изменения заявок, к которым привела команда) — именно из этого столбца при старте прогревается in-memory кеш (см. [Cache](#cache)).

Схема создаётся автоматически при старте приложения из файлов каталога `database/*.sql` (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`) — ручное создание таблиц через `psql` не требуется и не является поддерживаемым способом развёртывания.

### Индексы

Запросов, для которых нужно позаботиться о скорости поиска, три:

- **заявка по `order_id`** — уже покрыт первичным ключом `orders`, отдельный индекс не нужен;
- **команда по `command_id`** — тоже первичный ключ, на этот раз `processed_commands`;
- **выборка активных заявок при восстановлении книги** (`status IN ('OPEN', 'PARTIALLY_FILLED')`, упорядоченная по `sequence_number`) — под неё заведён отдельный **частичный** индекс `idx_orders_active_sequence ON orders (sequence_number) WHERE status IN ('OPEN', 'PARTIALLY_FILLED')` (`database/002_indexes.sql`).

Индекс сделан частичным, а не полным, потому что это единственный запрос, который его использует, и выполняется он один раз при старте процесса — не на горячем пути обработки команд. Со временем большинство строк `orders` окажется в статусе `FILLED` или `CANCELLED`: это заявки, которые уже отработаны и никогда не попадут под условие `WHERE`. Полный индекс по `sequence_number` рос бы вместе со всей таблицей, включая записи, которые в него фактически никогда не заглядывают; частичный индекс включает только строки, действительно нужные восстановлению, и не платит местом за историю уже закрытых заявок.

## Transactions

`PersistenceService` — единственный класс в проекте, где создаётся `PgTransaction`; на штатном пути одной изменяющей команды это делает `PersistenceService::save`. Внутри одной транзакции происходит запись в строго определённом порядке: сначала все `OrderChange` из `ExecutionResult` по очереди через `OrderRepository::save` (при `MODIFY` в списке оказываются два снимка одной и той же заявки — старая перед пересопоставлением и новая после, и порядок значим: побеждает тот, что применён последним), затем сделки через `TradeRepository::insert`, и в конце — запись о самой команде через `CommandRepository::save`. Порядок таблиц не случаен: `trades` ссылается на `orders` внешним ключом, значит заявки обязаны попасть в базу раньше сделок.

Второй метод, `PersistenceService::saveBatch`, устроен по тому же принципу (заявки → сделки → команды, одна транзакция), но применяется только к пакету из нескольких команд в режиме `--replay --batch` — это отдельный размен атомарности ради пропускной способности, подробно описанный в разделе [Оптимизации](#оптимизации-подготовленные-запросы-и-пакетная-запись); на обычном пути обработки одной команды он не используется.

Зачем нужна именно транзакция, а не последовательность независимых `INSERT`/`UPDATE`: без неё сбой ровно между двумя операциями — скажем, заявки уже обновлены, а часть сделок ещё нет — оставил бы книгу в памяти (уже изменённую сопоставлением) рассинхронизированной с тем, что видно в базе. При следующем восстановлении (см. [Recovery](#recovery)) из БД поднялось бы состояние, не совпадающее с тем, что было в памяти на момент сбоя: заявки или сделки потерялись бы молча, без единого сообщения об ошибке — то есть данные тихо разошлись бы. Одна транзакция на команду делает такое расхождение невозможным: либо заявки, сделки и отметка о команде фиксируются вместе, либо не фиксируется ничего.

Что происходит, если сбой всё же случается — уже после того, как книга в памяти изменена сопоставлением, но до успешного `COMMIT`. В проекте различаются два класса ошибок с разным поведением:

- доменные ошибки (`ParseError`, `OrderBookError`, `OrderError` и другие потомки `MatchingEngineError`, кроме `PersistenceError`) — печатают `ERROR:` в stderr, и обработка следующих команд продолжается. Это нормальная реакция на некорректный ввод одной конкретной команды, книга при этом не менялась.
- `PersistenceError` — сбой уже после изменения книги в памяти. Здесь одного отката транзакции недостаточно: `PgTransaction` откатывает то, что можно откатить на сервере (`ROLLBACK` в деструкторе, если не был вызван `commit()`), но память уже разошлась с базой, и откат БД это не лечит. Решение — fail-fast: ошибка пишется в лог, и процесс завершается, а не продолжает работу на расходящемся состоянии. Это сознательное решение проекта: попытка продолжить работу с уже разъехавшейся памятью и базой была бы хуже любого аварийного завершения — следующая команда работала бы над книгой, которой в базе не существует.

## Crash consistency

Вопрос здесь тот же, что и в [Transactions](#transactions), но с другим акцентом: что видно при следующем запуске после падения в произвольной точке обработки. Благодаря паре решений — атомарной транзакции на команду (см. выше) и тому, что состояние при старте собирается заново из БД, а не из памяти процесса (см. [Recovery](#recovery)) — состояние после падения всегда согласовано с последней **зафиксированной** транзакцией. Либо команда попала в базу целиком (изменения заявок, сделки, отметка в `processed_commands`), либо не попала вовсе — промежуточных состояний, где часть данных команды есть, а часть нет, попросту не существует.

Важно, что ни одно из двух решений само по себе этого не даёт. Одна транзакция без восстановления из БД ничего не значила бы: если бы состояние при старте бралось из памяти (снапшот процесса, сериализация в файл при выходе и так далее), крах посреди обработки всё равно потерял бы всё, что не успело попасть в этот снапшот, независимо от того, насколько аккуратно записана база. И наоборот — восстановление из БД без транзакционности читало бы ту же самую рассинхронизированную запись, которую описывает предыдущий раздел. Crash consistency в этом проекте — прямое следствие пары «одна транзакция на команду» + «восстановление из БД, а не из памяти процесса»: без любой из двух половин вторая ничего не гарантирует.

## Idempotency

`command_id` обязателен для любой изменяющей команды, но проверяется это не в парсере, а на уровне `CommandProcessor::process`/`processBatched` — если поле отсутствует или пусто, бросается `ParseError`. Парсер сознательно оставлен без этой проверки: он тестируется в базовой линии ДЗ-2 без `command_id`, и требование ДЗ-3 добавлено выше по стеку, не трогая уже закрытые тесты ядра сопоставления.

Поток обработки одной команды:

1. `command_id` отсутствует → ошибка, команда не выполняется.
2. `command_id` найден в `CommandCache` → возвращается результат прошлого выполнения этой же команды, книга заявок не трогается, в БД ничего не читается и не пишется.
3. Иначе — команда сопоставляется в памяти движком, результат сохраняется одной транзакцией БД (см. [Transactions](#transactions)), и только после успешного сохранения кладётся в кеш.

Ответ на вопрос ТЗ: при повторной отправке команды с тем же `command_id` книга заявок не меняется второй раз, новых сделок не возникает, а `processed_commands` не получает вторую строку (`command_id` — первичный ключ этой таблицы) — клиент получает в точности тот же результат, что и при первом выполнении. Распознаётся повтор по точному совпадению `command_id`, а не по содержимому команды: если тем же `command_id` придёт команда с другими полями, она всё равно будет опознана как повтор и вернёт старый результат, а не переисполнится с новыми параметрами.

## Cache

`CommandCache` — простое in-memory отображение `command_id → ExecutionResult` (`std::unordered_map` внутри). Размер кеша ничем не ограничен — это сознательное упрощение, а не оптимизация «на будущее»: задача учебная, объём команд за время жизни одного процесса заведомо не требует вытеснения, и неограниченный кеш проще любой схемы с TTL или LRU. Цена этой простоты — память кеша растёт линейно вместе с числом обработанных команд и не освобождается до завершения процесса.

При старте кеш прогревается: `RecoveryService` вызывает `CommandRepository::loadAll`, читающий все строки `processed_commands`, и для каждой — `CommandProcessor::warmCache`, который разбирает `result` (JSONB) обратно в `ExecutionResult` тем же кодом, что и сериализует его при сохранении (`CommandProcessor::parseResult`/`serializeResult` — прямое и обратное преобразование живут рядом в одном файле, чтобы не разойтись форматом). После прогрева кеш в памяти содержит результаты всех команд, когда-либо примененных к этой базе, — не только тех, что пришли в текущем запуске.

Ключевое для дешёвой идемпотентности: проверка на повтор идёт прежде всего в памяти — `CommandCache::find` вызывается раньше любого обращения к БД. Если команда уже в кеше, к базе вообще не идёт ни один запрос; поход в БД случается только для по-настоящему новых команд.

## Recovery

Старт приложения проходит через пять этапов в фиксированном порядке, видном по строкам лога. Первые два — подключение к БД и применение схемы (`database/*.sql`) — выполняются в `Application::run` ещё до вызова восстановления; дальше уже готовое, живое соединение передаётся в `recoverState` (`RecoveryService`), которая делает остальное:

1. подключение к БД и применение схемы (`Application::run`, до восстановления);
2. чтение активных заявок — `OrderRepository::loadActive` выбирает только заявки со статусом `OPEN` или `PARTIALLY_FILLED`, явно упорядочивая их `ORDER BY sequence_number ASC` (не полагаясь на порядок строк, в котором их вернул бы `SELECT` без сортировки);
3. восстановление книги — каждая прочитанная заявка кладётся в `OrderBook` через `CommandProcessor::restoreOrder`/`MatchingEngine::restore`;
4. восстановление счётчика номеров — `SequenceGenerator` перезаводится на максимум `sequence_number` **по всей таблице `orders`**, а не только по активным заявкам: исполненная или отменённая заявка может иметь номер выше любой из ещё активных, и без учёта этого первая же новая заявка после рестарта столкнулась бы с ограничением `UNIQUE` на этом столбце;
5. прогрев кеша идемпотентности — см. [Cache](#cache).

Этапы 2–5 выполняет именно `recoverState`, последовательно и в этом порядке.

**Почему восстановленные заявки не проходят сопоставление заново** (REQ-REC-04). `OrderBook::restore`/`MatchingEngine::restore` кладут уже готовую заявку прямо в книгу, минуя `match`/`matchMarket`. Если бы это было не так, два восстановленных встречных ордера, оказавшиеся в книге друг напротив друга, пересопоставились бы между собой и породили бы сделку, которой на самом деле не было, — фантомную, придуманную самим процессом восстановления, а не рынком.

**Почему приоритет по времени сохраняется после рестарта.** `OrderBook` сам по себе ничего не знает о `sequence_number` — заявки внутри одного ценового уровня лежат в обычном `std::deque`, и `addOrder`/`restore` просто дописывают в конец (`push_back`). Порядок в этом `deque` — это порядок вызовов, а не порядок какого-либо поля. Именно поэтому сохранение приоритета по времени целиком лежит на восстановлении, а не на самой книге, и держится на двух вещах вместе:

1. восстанавливающий конструктор `Order` принимает `sequence_number` таким, каким он был прочитан из БД, и не обращается к `SequenceGenerator` за новым значением — заявка после рестарта несёт тот же номер, что и до падения;
2. `OrderRepository::loadActive` явно читает заявки `ORDER BY sequence_number ASC`, и `recoverState` кладёт их в книгу в этом же порядке, вызовом за вызовом.

Если бы пункт 2 исчез — например, `loadActive` вернула бы строки в порядке, в котором их хранит база, без явного `ORDER BY`, — приоритет по времени сломался бы, даже несмотря на то, что каждая заявка по-прежнему несла бы свой правильный `sequence_number`: сам номер книгу ни на что не сортирует, он просто едет вместе с заявкой как данные. Две заявки с одинаковой ценой после восстановления оказываются в правильном порядке не потому, что `OrderBook` их сортирует, а потому что их в этом порядке принесли снаружи.

## RAII wrapper

Проекту запрещён `libpqxx` (REQ-RAII-01/02) — допускается только чистый C API `libpq`, а он не управляет ресурсами сам: `PGconn*` и `PGresult*` нужно освобождать вручную (`PQfinish`, `PQclear`), и любое исключение между получением ресурса и его освобождением привело бы к утечке. Отсюда собственная тонкая обёртка — `PgConnection`/`PgResult`/`PgTransaction`.

Владение реализовано через `std::unique_ptr` с собственными удалителями: `PgConnectionDeleter` вызывает `PQfinish`, аналогичный удалитель у `PGresult` вызывает `PQclear`. Освобождение сосредоточено в одном месте на тип ресурса, а не разбросано по всем местам, где ресурс мог бы использоваться.

`PgConnection` некопируем и перемещаем, но операции перемещения не помечены `noexcept` и не сгенерированы через `= default` — они проверяют счётчик активных транзакций (`activeTransactionCount_`) на перемещаемом объекте и бросают `DatabaseError`, если он не нулевой. Причина: перемещение соединения с живой (не закоммиченной и не разрушенной) `PgTransaction` опустошило бы `conn_` под её ссылкой, и `ROLLBACK` в деструкторе транзакции либо ушёл бы в неопределённое поведение на пустом соединении, либо бросил бы исключение, которое в деструкторе некому поймать, кроме проглатывающего `catch(...)`, — оставляя транзакцию висеть на сервере незамеченной.

`PgTransaction` реализует ровно ту гарантию, которая нужна остальному проекту: `BEGIN` выполняется в конструкторе, `commit()` — явный вызов, а если между началом транзакции и вызовом `commit()` вылетает исключение, деструктор откатывает её `ROLLBACK`-ом сам, без участия вызывающего кода. Это и даёт атомарность из раздела [Transactions](#transactions) без ручного `try/catch` вокруг каждой транзакции.

Наконец, `PGconn` и `PGresult` не выходят за пределы `pg_connection.*`/`pg_result.*`: заголовки объявляют только тег структуры (`struct pg_conn;`) вместо включения `<libpq-fe.h>`, поэтому типы драйвера физически не видны транзитивно ни репозиториям, ни `MatchingEngine`, ни `Application` — они получают на вход только ссылку на `PgConnection` и работают с ней через методы `execute`/`executePrepared`, не подозревая о существовании libpq за этой границей.

## Производительность и профилирование

Раздел закрывает REQ-PERF-01, REQ-PERF-03, REQ-PERF-04 и REQ-OPT-01. Все числа ниже получены реальными запусками на нагрузке из 100 000 команд (`workload.jsonl`, зерно генератора 42), а не оценены на глаз.

Сборка на момент замера — `RelWithDebInfo` (`-O2 -g`, символы не стрипнуты). До профилирования проект собирался как `Release` (`-O3 -DNDEBUG`, без отладочной информации), и ради профилирования конфигурация была изменена: без символов в отчёте были бы адреса вместо имён функций. После переконфигурации весь набор тестов прогнан заново и проходит в новой конфигурации. Все замеры этого и следующего разделов сняты в `RelWithDebInfo` — «до и после» сравнимы только в одной и той же конфигурации. **Текущее умолчание проекта — снова `Release`** (см. раздел [Сборка](#сборка)): для воспроизведения профиля с именами функций конфигурацию нужно задать явно, `cmake -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo`.

### Проверка памяти: Valgrind и цель сборки `memcheck`

Приложение проверено на штатном сценарии, задействующем подключение к БД, применение схемы, транзакционную запись заявок и сделки и штатное завершение:

```
valgrind --leak-check=full --show-leak-kinds=all ./build/matching_engine '<json с двумя встречными заявками и PRINT>'
```

| Величина | Значение |
|---|---|
| `definitely lost` | 0 байт в 0 блоках |
| `indirectly lost` | 0 байт в 0 блоках |
| `possibly lost` | 0 байт в 0 блоках |
| `still reachable` | 262 байта в 6 блоках |
| `ERROR SUMMARY` | 0 ошибок |

Утечек, созданных кодом проекта, нет. Оставшиеся 262 байта в шести блоках принадлежат не проекту: все шесть происходят из одной цепочки `PQsetdbLogin → PQconnectPoll`, то есть из однократной инициализации GSSAPI/Kerberos и таблиц методов OpenSSL внутри libpq при первом рукопожатии с сервером. Это статические кеши библиотек, живущие до конца процесса по их собственной конструкции. Что они не накапливаются, проверено сравнением: набор из шести блоков одинаков и на сценарии из трёх команд, и на прогоне 200 команд в режиме `--replay`, и на полном прогоне тестового набора, актуального на момент замера — то есть он не зависит ни от числа запросов, ни от числа транзакций.

Ресурсы самого проекта освобождаются деструкторами: `PGconn` и `PGresult` живут под `std::unique_ptr` с собственными удалителями (`PQfinish` и `PQclear`), незакоммиченную транзакцию откатывает деструктор `PgTransaction`.

Весь набор тестов запускается под Valgrind одной командой:

```
cmake --build build --target memcheck
```

Цель вызывает `valgrind` напрямую на тестовом бинарнике с `--error-exitcode=1`, а не через `ctest -T memcheck`: последний не связывает найденные дефекты с кодом возврата, и такая цель была бы зелёной всегда. На исправном коде цель завершается кодом 0. Её работоспособность проверена внесением заведомой утечки: цель обнаружила 27 648 байт в 108 блоках, `ERROR SUMMARY: 103 errors`, и сборка завершилась ненулевым кодом; после снятия утечки цель снова зелёная.

### Способ снятия профиля (REQ-PERF-03, критерий 6)

`kernel.perf_event_paranoid = 2` — аппаратные счётчики (`cycles`, `instructions` и т. п.) в этом окружении (WSL2) недоступны: `perf record` с ними не программируется. Профиль снят программным событием `cpu-clock`, и из-за того же `paranoid = 2` охват — только пользовательское пространство (в отчёте это видно по имени события `cpu-clock:u`, суффикс `:u`). Время, проведённое в ядре (системные вызовы, в том числе сетевой ввод-вывод с PostgreSQL), в такой профиль не попадает в принципе — это ограничение метода, а не находка о коде.

```
perf record -e cpu-clock -g -o perf.data -- ./build/matching_engine --replay workload.jsonl
perf report -i perf.data --stdio --sort=overhead,symbol -g none
```

Профиль собран на 100 000 команд, 61 626 отсчётов события `cpu-clock:u`.

|---|---|

86,6% времени прогона процесс не выполняет код ни в пользовательском, ни в ядерном режиме — он заблокирован на чтении из сокета, ожидая ответа PostgreSQL. Отдельный прогон под `perf record` (тот же файл нагрузки, база тоже была предварительно очищена) показал внутренний таймер приложения 376 808 мс — заметно меньше, чем в прогоне без `perf`. Это не ошибка и не более быстрая конфигурация: два прогона к PostgreSQL по сети закономерно колеблются по времени ожидания (тёплый кеш страниц ОС и буферный кеш PostgreSQL после первого прогона, общая загруженность WSL2-хоста). Оба числа получены реальными запусками; для параметра «сколько всего занимает прогон» ориентир — прогон с `/usr/bin/time -v` (в нём же есть разбивка user/sys), а не более быстрый прогон под `perf`.

### Ответы на четыре вопроса ТЗ

**1. Какие функции занимают больше всего процессорного времени.** `malloc` (4,42%) и связанные с ним примитивы работы с памятью и строками — `__memmove_evex_unaligned_erms`, `cfree`, `_int_free`, `__strcmp_evex`, `__memcmp_evex_movbe` — вместе это самая тяжёлая группа (≈33% CPU-профиля). Дальше идёт поиск в кеше идемпотентности (1,40%) и код одного репозитория — `OrderRepository::save` (1,35%). Это не адреса, а разрешённые имена: `RelWithDebInfo` дал полную символизацию.

**2. Сколько занимает собственно сопоставление.** Функции `OrderBook`/`MatchingEngine`/`Order::fill`/`Order::cancel` вместе — около 2,9% CPU-профиля. В пересчёте на пользовательское время прогона (36,49 с из `time -v`) это ≈1,06 с суммарно на все 100 000 команд — то есть **на два порядка меньше**, чем время, потраченное на ожидание БД. Сопоставление в этой системе не является узким местом ни разу.

**3. Сколько — работа с PostgreSQL.** Здесь два разных числа, и путать их нельзя. В CPU-профиле (программное событие, только пользовательское время) на путь к БД уходит: собственный код репозиториев и обёрток над `libpq` (≈3,7%) + сам `libpq` (≈3,5%) + шифрование TLS-соединения (≈12,8%) — итого ≈20% CPU-профиля, то есть даже в пределах маленького процессорного бюджета работа с БД тяжелее, чем сопоставление, примерно в 7 раз. Но это не главный ответ: реальная стоимость работы с БД — это 86,6% *всего времени прогона* (552,43 с из 638,01 с), проведённые в ожидании ответа PostgreSQL по сокету, — время, которое CPU-профиль в принципе не видит, потому что процесс в этот момент не выполняется ни на одном ядре.

**4. Есть ли неожиданные горячие места.**
   - **TLS-шифрование соединения с БД — ≈12,8% CPU-профиля**, хотя в коде проекта (`pg_connection.cpp`) SSL нигде явно не запрашивается. `PQsetdbLogin` не получает `sslmode`, поэтому используется значение по умолчанию `prefer`; локальный сервер PostgreSQL в этом окружении держит `ssl = on` (`SHOW ssl` → `on`, `pg_stat_ssl.ssl` → `t` даже для обычного `psql`-подключения), поэтому каждый раунд-трип к БД в приложении реально шифруется. Это не ошибка кода, а побочный эффект настройки локального сервера — но именно тот случай, когда профиль показывает то, что не видно по исходникам.
   - **Приглушённые логи не бесплатны.** `SPDLOG_LEVEL=off` подавляет вывод, но не построение сообщения: `Logger::info` (`src/logger.cpp`) принимает уже готовую `std::string`, а строки вроде `"Trade executed: buy=" + std::to_string(buyId) + ...` в `matching_engine.cpp` (15 мест только в этом файле) собираются оператором `+` и `std::to_string` заранее, до того как `spdlog` успевает проверить уровень и отбросить сообщение. Отдельно измерить долю именно этого в 33%-й группе аллокаций/строк не удалось (в профиле функция вызова не отличима от остальных источников временных строк — параметров SQL-запросов и сериализации JSON), но структурно это реальный источник лишней работы, который не исчезает от приглушения уровня лога.
   - Идемпотентный кеш (поиск по `command_id` в `std::unordered_map`) — 1,40% CPU-профиля сам по себе не аномалия (это ожидаемая цена идемпотентности), но заметно выше, чем всё сопоставление целиком, — стоит держать в уме при последующей оптимизации.

### Что дальше

Дальнейшая оптимизация (подготовленные запросы, пакетная запись) должна целиться не в CPU-профиль — там оптимизировать почти нечего, сопоставление и так дёшево, — а в 86,6% времени ожидания и в число раунд-трипов на команду. Здесь профилирование не даёт готового решения, только подтверждает, где искать: каждая команда — это несколько последовательных `PQexecParams` в одной транзакции, и именно их количество (а не их внутренняя стоимость) определяет итоговые 6 мс на команду.

## Оптимизации: подготовленные запросы и пакетная запись

Раздел закрывает REQ-OPT-02 и REQ-OPT-03: что было, почему это стоило столько и что стало. Обе оптимизации внесены в код репозиториев, `Application` и `CommandProcessor`; здесь — только измерения и выводы.

### Методика

Сборка та же, что и в предыдущем замере: `RelWithDebInfo` (`-O2 -g`), не переконфигурировалась. Три варианта:

1. **было** — бинарник, собранный из состояния до внедрения подготовленных запросов и пакетной записи (без `executePrepared`/`PQexecPrepared` в символах), т. е. без обеих оптимизаций;
2. **prepared** — текущий `matching_engine`, обычный `--replay` (без `--batch`) — только подготовленные запросы;
3. **batch** — текущий `matching_engine --replay --batch`, размер пакета 500 команд (константа `kReplayBatchSize` в `src/application.cpp`). Несмотря на общий бинарник с вариантом 2, эффект здесь — только от пакетной записи: `saveBatch`/`insertBatch` идут через обычный `execute()`, подготовленные запросы (`executePrepared`) в этом пути не вызываются ни разу — их использует только `save()`/`insert()` штатного пути.

Нагрузка для контролируемого сравнения — 20 000 команд (зерно генератора 42, файл `bench20k.jsonl`, не входит в репозиторий). **Три прогона на каждый вариант**, между прогонами:

```
psql -h <host> -p <port> -U <user> -d <database> -c "TRUNCATE orders, trades, processed_commands"
```

Логи приглушены `SPDLOG_LEVEL=off`, как и в предыдущем замере. После каждого прогона сводка `REPLAY SUMMARY` сверялась с БД: `processed` — с числом строк `processed_commands`, `trades` — с числом строк `trades`. Во всех 9 контрольных прогонах на 20 000 командах совпадения были точными: `processed=20000`, `trades=6634` — и в таблицах, и в сводке, ни разу расхождения.

Дополнительно — по одному прогону варианта 2 и 3 на полном `workload.jsonl` (100 000 команд, зерно 42); тоже сверено с БД (`processed=100000`, `trades=33447` в обоих случаях). Для варианта 1 на полном файле новый прогон не делался — используется число из предыдущего замера, **638,01 с** общего времени (там же сказано, что между прогонами того же бинарника и файла разброс достигает почти 40%, поэтому это число — ориентир, а не точная опорная точка).

### Prepared statements: было → причина → стало

**Было.** Каждая изменяющая команда выполняла upsert заявки / вставку сделки / вставку записи `processed_commands` через `PQexecParams` с текстом запроса. PostgreSQL разбирает и строит план заново на каждый такой вызов, даже если текст запроса от вызова к вызову не меняется ни на символ.

**Причина стоимости.** Повторный parse/plan на сервере на каждый из трёх горячих запросов, повторяющихся на каждой команде.

**Стало.** Три горячих запроса (`OrderRepository::save`, вставка сделки, вставка `processed_commands`) готовятся один раз на сессию через `PQprepare` (`PgConnection::executePrepared`) и дальше вызываются по имени через `PQexecPrepared`. Параметры по-прежнему передаются отдельным массивом — конкатенации значений в текст запроса нет.

**Число.** Медианное время на bench20k (3 прогона, `elapsed_ms` из сводки):

| Вариант | Прогон 1 | Прогон 2 | Прогон 3 | Медиана | Мин–макс (разброс) |
|---|---|---|---|---|---|
| было | 74 010 мс | 75 276 мс | 76 608 мс | 75 276 мс | 74 010–76 608 мс (≈3,4%) |
| prepared | 74 004 мс | 72 978 мс | 75 941 мс | 74 004 мс | 72 978–75 941 мс (≈4,0%) |

Разница медиан — 1,7% (75 276 → 74 004 мс), то есть **меньше собственного разброса каждого из двух вариантов** (3,4% и 4,0%). На этом бенче эффект от prepared statements не отделяется от шума измерения — честный нулевой результат, а не ошибка: узкое место, как и было установлено предыдущим профилированием, не разбор запроса на сервере, а сетевые раунд-трипы и ожидание ответа PostgreSQL (86,6% времени прогона в предыдущем замере — не CPU, а ожидание сокета). Экономия на parse/plan реальна, но на локальной сети она на два порядка меньше стоимости самого раунд-трипа, поэтому тонет в его дисперсии.

На полном `workload.jsonl` (100 000 команд, один прогон, не три) разница выглядит заметнее: 638,01 с (было, число из предыдущего замера) против 502,42 с сейчас (≈27% быстрее). Это наблюдение, а не доказательство: два числа сняты в разных сессиях, без повторов, и предыдущий замер сам показал на этом же файле разброс до 40% между прогонами одного и того же бинарника. Опорный вывод по prepared statements — контролируемое сравнение на bench20k выше (эффект не отличим от шума), а не эта разница.

### Пакетная запись: было → причина → стало

**Было.** Без пакетной записи каждая изменяющая команда — своя транзакция: `BEGIN`, upsert заявки, вставка сделки (если она была), вставка `processed_commands`, `COMMIT`. Несколько раунд-трипов и одна фиксация (с ожиданием её подтверждения сервером) на каждую команду.

**Причина стоимости.** Не сам SQL, а число раунд-трипов по сети и число `COMMIT` — каждый `COMMIT` в PostgreSQL ждёт подтверждения записи в WAL.

**Стало.** В режиме `--replay --batch` сопоставление и запись в кеш идемпотентности (`CommandProcessor::processBatched`) выполняются как обычно, сразу — а запись в БД откладывается: команды копятся в памяти, и раз в 500 накопленных команд (`Application::runReplay`, остаток — после конца файла) весь пакет сохраняется одной `PgTransaction`: сначала все изменения `orders` одним многострочным `INSERT ... VALUES (...), (...), ... ON CONFLICT DO UPDATE` (`OrderRepository::saveBatch`, со свёрткой повторных изменений одного `order_id` — PostgreSQL не даёт обновить одну строку дважды в одном `ON CONFLICT`), затем все `trades` одним запросом, затем все `processed_commands` — и один `COMMIT` на весь пакет. Параметры и здесь передаются отдельным массивом, значения в текст запроса не подставляются — только номера плейсхолдеров `$1..$N`. Все три запроса идут через обычный `execute()`, а не через `executePrepared()` из предыдущего раздела: форма многострочного `INSERT` зависит от числа строк в пакете, готовить её впрок как подготовленный запрос незачем — то есть эффект ниже даёт исключительно сокращение числа `COMMIT`, а не разбор/план запроса.

**Число (время).**

| Вариант | Прогон 1 | Прогон 2 | Прогон 3 | Медиана | Мин–макс (разброс) |
|---|---|---|---|---|---|
| prepared (без batch) | 74 004 мс | 72 978 мс | 75 941 мс | 74 004 мс | 72 978–75 941 мс |
| batch | 1 281 мс | 1 359 мс | 1 143 мс | 1 281 мс | 1 143–1 359 мс |

Ускорение на bench20k: 74 004 / 1 281 ≈ **×57,8** к варианту без batch, 75 276 / 1 281 ≈ **×58,8** к варианту «было». На полном `workload.jsonl` (100 000 команд, один прогон каждого варианта в одной и той же сессии — это корректное прямое сравнение, в отличие от сравнения с вариантом «было»): 502,42 с (без batch) → 7,54 с (с batch), ускорение ≈ **×66,6**.

**Число (транзакции сервера, `pg_stat_database.xact_commit`, bench20k, 20 000 команд).** Дельта коммитов за прогон с предварительно очищенной БД:

| Вариант | Δ `xact_commit` | Комментарий |
|---|---|---|
| без `--batch` | 20 030 | ≈1,0015 коммита на команду — «одна команда = одна транзакция» с точностью до нескольких служебных коммитов при старте (применение схемы, подключение) |
| с `--batch` | 48 | 20 000 / 500 = 40 пакетов + 8 тех же служебных коммитов — не зависит от числа команд внутри пакета |

Именно сокращение числа коммитов (и подтверждений записи в WAL), а не более быстрый SQL для отдельной команды, объясняет ускорение: каждая команда в пакетном режиме выполняет тот же upsert/insert, что и раньше, но не ждёт индивидуального подтверждения фиксации после каждой из них. Это согласуется с независимым замером меньшего масштаба (2000 команд, тот же счётчик сервера): 2008 коммитов без `--batch` против 12 с `--batch` (4 пакета + 8 служебных) — то же соотношение, что и на 20 000 командах.

### Размен атомарности в пакетном режиме

Пакетный режим осознанно нарушает REQ-TX-02 («одна команда — одна транзакция»): в `--batch` до 500 команд разделяют одну транзакцию, и сбой в середине пакета — например, `PersistenceError` при сохранении одной из команд накопленного пакета — откатывает разом **все** команды пакета, а не только неудачную. Это осознанный размен атомарности на пропускную способность, и он ограничен так, чтобы не задеть штатный путь:

- пакетная запись включается **только** в режиме воспроизведения нагрузки и **только** явным ключом `--batch`; без `--replay` ключ `--batch` — ошибка разбора аргументов (`Option --batch requires --replay`), сам процесс не запускается;
- без ключа `--batch` (в том числе в обычном `--replay`) `Application::processCommand` вызывает тот же `CommandProcessor::process`/`PersistenceService::save`, что и до внедрения подготовленных запросов и пакетной записи, без единого изменения в этом пути — транзакция на команду сохраняется;
- это подтверждено числами транзакций выше, а не только текстом кода: без `--batch` дельта `xact_commit` практически равна числу обработанных команд (20 030 на 20 000), с `--batch` она равна числу пакетов плюс постоянные служебные коммиты (48 = 40 × 500-команд-пакетов + 8), а не числу команд — то есть на сервере наблюдаема именно разница в гранулярности транзакций, а не только в декларируемом поведении.

Значит пакетный режим годится для измерений производительности воспроизведения нагрузки, но не для штатной обработки: там, где важна атомарность на уровне отдельной команды (обычный запуск, обычный `--replay` без `--batch`), поведение не менялось.
