# ДЗ-4 — Matching Engine как Linux Service: требования

Требования ДЗ-4, разложенные по группам. У каждого требования свой идентификатор, чтобы на него можно было сослаться в коммите, тесте или обсуждении.

Статусы: `TODO` — не начато, `В РАБОТЕ`, `ГОТОВО`.

Требования выведены из текста задания. Группа `EXT` соответствует дополнительным заданиям — они взяты в работу целиком, а не выборочно.

## NET — TCP-сервер и сессии

| ID | Требование | Статус |
|---|---|---|
| REQ-NET-01 | Matching Engine работает как TCP-сервер: принимает подключения клиентов и не завершается после обработки команды | ГОТОВО |
| REQ-NET-02 | Сетевой слой реализован на Boost.Asio | ГОТОВО |
| REQ-NET-03 | Используется асинхронный интерфейс: `async_accept`, `async_read`, `async_write` | ГОТОВО |
| REQ-NET-04 | Активный цикл опроса сокета (`while (true) { if (socketHasData()) ... }`) отсутствует | ГОТОВО |
| REQ-NET-05 | Одно TCP-соединение представлено отдельным объектом `Session` | ГОТОВО |
| REQ-NET-06 | `Session` отвечает за сокет, чтение заголовка кадра, чтение тела кадра, разбор запроса, отправку ответа и время жизни соединения | ГОТОВО |
| REQ-NET-07 | Время жизни сессии управляется через `std::shared_ptr` и `std::enable_shared_from_this`; сессия не уничтожается, пока для неё есть незавершённые асинхронные операции | ГОТОВО |
| REQ-NET-08 | Выделен класс `Server`, управляющий acceptor, сессиями, запуском и остановкой | ГОТОВО |
| REQ-NET-09 | Отправка ответов упорядочена: новая асинхронная запись не начинается до завершения предыдущей на том же сокете | ГОТОВО |
| REQ-NET-10 | Разрыв соединения клиентом обрабатывается штатно и не приводит к утечке ресурсов или падению сервера | ГОТОВО |
| REQ-NET-11 | Сетевой код отделён от Matching Engine: `MatchingEngine` и `OrderBook` не знают о сокетах, Boost.Asio и формате кадров | ГОТОВО |
| REQ-NET-12 | Сервер запускается командой вида `matching-engine-server --config <путь>` | ГОТОВО |
| REQ-NET-13 | При старте сервер сообщает о готовности и адресе прослушивания (например, `Listening on 0.0.0.0:9000`) | ГОТОВО |
| REQ-NET-14 | Порядок запуска: подключение к PostgreSQL → восстановление Order Book → прогрев кеша → начало прослушивания порта | ГОТОВО |

## PROTO — Формат кадра и кодек

| ID | Требование | Статус |
|---|---|---|
| REQ-PROTO-01 | Реализован собственный framing protocol; сервер не полагается на границы TCP-чтения | ГОТОВО |
| REQ-PROTO-02 | Формат кадра: 4 байта размера полезной нагрузки (`uint32_t`), затем ровно N байт JSON | ГОТОВО |
| REQ-PROTO-03 | Размер передаётся в сетевом порядке байт | ГОТОВО |
| REQ-PROTO-04 | Выделен отдельный компонент (`MessageCodec` или `Protocol`) с операциями кодирования и декодирования | ГОТОВО |
| REQ-PROTO-05 | Работа с wire format локализована в кодеке: `memcpy`, `htonl`, `ntohl` не встречаются в сессии, сервере и клиенте | ГОТОВО |
| REQ-PROTO-06 | Одно сообщение, пришедшее несколькими частями, собирается корректно | ГОТОВО |
| REQ-PROTO-07 | Несколько сообщений, пришедших одним куском, обрабатываются все | ГОТОВО |
| REQ-PROTO-08 | Определён максимальный размер сообщения (`MAX_MESSAGE_SIZE`, ориентир — 1 МБ) | ГОТОВО |
| REQ-PROTO-09 | Размер проверяется **до** выделения памяти под полезную нагрузку: заявленные клиентом 2 ГБ не приводят к попытке выделить 2 ГБ | ГОТОВО |
| REQ-PROTO-10 | При превышении максимального размера соединение корректно закрывается либо возвращается ошибка протокола | ГОТОВО |

## API — Команды и ответы

| ID | Требование | Статус |
|---|---|---|
| REQ-API-01 | Команды `ADD`, `CANCEL`, `PRINT` доступны через TCP | ГОТОВО |
| REQ-API-02 | Реализованные ранее `MODIFY` и `MARKET` также работают через сетевой API | ГОТОВО |
| REQ-API-03 | Ответ на успешную изменяющую команду содержит `command_id`, `status: OK`, `order_id` и массив `trades` — как в примерах задания; элемент `trades` несёт `buy_order_id`, `sell_order_id`, `price`, `quantity` | ГОТОВО |
| REQ-API-04 | Добавлена служебная команда `PING` с ответом `{"status":"OK","result":"PONG"}` | ГОТОВО |
| REQ-API-05 | `PING` не сохраняется в PostgreSQL, не требует `command_id` и не изменяет Order Book | ГОТОВО |
| REQ-API-06 | Ответ на ошибочную команду содержит `status: ERROR`, поле `error` с кодом ошибки и поле `message` с человекочитаемым описанием — оба на верхнем уровне объекта, как в примерах задания | ГОТОВО |
| REQ-API-07 | Ошибки пользователя не приводят к завершению сервера и не разрывают другие соединения | ГОТОВО |
| REQ-API-08 | Ответ на команду `PRINT` передаёт состояние книги заявок в машиночитаемом виде, достаточном для проверки восстановления | ГОТОВО |
| REQ-API-09 | Повторная команда с тем же `command_id` возвращает **тот же ответ**, что и первое выполнение | ГОТОВО |
| REQ-API-10 | Имена полей запроса совпадают с примерами задания: идентификатор заявки передаётся как `order_id` | ГОТОВО |

## THR — Потоки, сигналы и завершение

| ID | Требование | Статус |
|---|---|---|
| REQ-THR-01 | Приложение многопоточное: существует минимум два потока | ГОТОВО |
| REQ-THR-02 | Сетевой поток обслуживает Boost.Asio: accept, чтение, запись, обработку сетевых событий | ГОТОВО |
| REQ-THR-03 | Отдельный поток занимается ожиданием системных сигналов | ГОТОВО |
| REQ-THR-04 | Обрабатывается `SIGTERM`; также обрабатывается `SIGINT` | ГОТОВО |
| REQ-THR-05 | Сложная C++-логика внутри POSIX-обработчика сигнала отсутствует | ГОТОВО |
| REQ-THR-06 | Завершение программы через `std::exit` из обработчика сигнала не используется | ГОТОВО |
| REQ-THR-07 | Выделен отдельный класс, отвечающий за сигналы и запрос на остановку | ГОТОВО |
| REQ-THR-08 | Сигнальный поток не изменяет состояние Matching Engine напрямую, а передаёт событие остановки владельцу сервера | ГОТОВО |
| REQ-THR-09 | Явно определено, какой поток владеет какими данными; изменяемое состояние движка принадлежит одному потоку | ГОТОВО |
| REQ-THR-10 | `std::mutex` не применяется там, где разделение данных не требуется | ГОТОВО |
| REQ-THR-11 | Graceful shutdown по `SIGTERM`: прекращение приёма новых соединений → остановка сетевого цикла → корректное закрытие активных соединений → завершение или безопасная отмена текущей операции → освобождение ресурсов PostgreSQL → завершение рабочих потоков → выход с кодом `0` | ГОТОВО |
| REQ-THR-12 | Все рабочие потоки присоединяются при завершении; исключение не покидает поток | ГОТОВО |
| REQ-THR-13 | В коде проекта отсутствуют состояния гонки | ГОТОВО |
